Every verdict this pipeline produces is only as good as the map it reasoned over. That map is the operational graph — a living picture of every server, service, database, switch and disk in an estate, and how they depend on each other. This tab is the plain-language walk of the map chapter §3. The technical term on each card is what you’ll see on the Pipeline & Graph tab and in that chapter.

The short version

Most monitoring tools can show you a topology map. The difference here: every line on our map comes with a receipt — where we got it, how sure we are, and when we last checked. A map without receipts is just a guess with good graphics.

How sure are we about a connection?

Every relationship on the map (“this app runs on this server,” “this server talks to that database”) is tagged with one of three confidence tiers — not a single trust score, but three genuinely different kinds of evidence:

  1. 1

    We asked the source directly

    authoritative

    The strongest kind. Example: we asked the hypervisor which virtual machines are running on it, right now. As solid as evidence gets.

  2. 2

    Someone told us, and we never checked

    declared

    Example: a CMDB record says this server belongs to that cluster. Could be true. Could be two reorganizations out of date — nothing is watching it to find out.

  3. 3

    We inferred it from watching behavior

    corroborating

    Example: this app keeps talking to that database over the network, so we infer a dependency. Genuinely useful — but it's a pattern, not a fact.

A verdict is only as strong as the weakest tier it had to walk through to reach its answer. Whether that formally caps the confidence score shown to an operator is still an open decision (see the HLD's decision log, #3).

A. Signal classes — the 13 kinds of telemetry a CI can emit

Every node in ci_telemetry[] carries all 13 classes, each marked applicable: true|false — and when false, a stated reason. This is a deliberate superset of MELT (Metrics/Events/Logs/Traces): it also covers config/topology, change, code-level profiles, security posture, real-user sessions and physical sensors, because a real RCA pipeline needs all of those to localize and corroborate a fault, not just the four classic pillars.

1. Availability

availability

Is this CI up, down, unreachable or degraded — the binary/tri-state gate. Down flips every dependent to “presumed unreachable.”

Linuxlinux-server.up, polled 30s from /proc & /sys — 1=up, 0=down.
K8sPod status.phase / Ready condition, rolled up as kube_pod_status_phase.

2. Performance

performance

The four golden signals — latency, traffic, errors, saturation — as continuous time-series metrics.

Linuxsystem.cpu.utilization, system.disk.io.latency via node_exporter/agent.
K8scontainer_cpu_usage_seconds_total, container_memory_working_set_bytes via cAdvisor.

3. Logs

logs

Unstructured/semi-structured text, mined with regex key_patterns each tagged to a named failure mode.

Linuxjournald line Out of memory: Killed process → event_type: oom_kill.
K8scontainer stdout via Fluent Bit; terminated-state reason OOMKilled on the container status.

4. Traces

traces

Distributed spans showing one request's hop-by-hop path across services, with parent/child timing.

Linuxnot applicable to the OS/host CI itself — applies to the JVM/app running on it.
K8sOTel span via Envoy sidecar: service.name: checkout → peer.service: payments.

5. Flows/Packets

flows_packets

Network flow records — who talked to whom, how much, and whether packets dropped or retransmitted.

Linuxconntrack 5-tuple entries on the host.
K8sCilium Hubble / CNI flow between two pod IPs, identity-resolved on both ends.

6. Events

events

Discrete, timestamped state-change notifications — distinct from continuous metrics or free-text logs.

Linuxsystemd “unit entered failed state” journal event, keyed by systemd.unit.
K8sKubernetes Event object: Warning BackOff restarting failed container.

7. Synthetic

synthetic

Active, scripted probes that check a CI from outside on a schedule, instead of waiting for real traffic to reveal a fault.

Linuxnot applicable to the host itself — applies to nginx-web-server as an HTTP check.
K8ssynthetic GET against an Ingress endpoint, or a livenessProbe/readinessProbe result.

8. Config/Topology

config_topology

Discovery and inventory data used to find relationships — the raw material E3 turns into typed edges.

LinuxLLDP neighbor table: lldpRemSysName, lldpRemPortId.
K8skube-state-metrics ownership refs: kube_pod_owner{owner_kind="ReplicaSet"}.

9. Change/Deployment

change_deployment

What changed on this CI and when — packages, config, kernel, orchestrated runs — so RCA can ask “what changed right before this broke.” See the correlation field below.

Linuxdnf/yum history package transaction, config-mgmt (Ansible) run.
K8sDeployment rollout / new image digest applied; ArgoCD sync event.

10. Profiles

profiles

Continuous/eBPF code-level profiling — which function is actually burning the resource, one level below a metric.

Linuxparca-agent/perf record on-CPU stack sample.
K8ssame eBPF profiler as a DaemonSet, profiles keyed by pod/container instead of bare host.

11. Security/Posture

security_posture

Vulnerability, patch, hardening and detection state — risk context that can itself be the root cause.

LinuxCVE scanner result against installed host packages.
K8simage vuln scan (Trivy) against the pod's image; Pod Security admission posture.

12. RUM

rum

Real User Monitoring — actual end-user browser/mobile session telemetry. Only applicable to user-facing CIs.

Linuxnot applicable — a bare OS host is never user-facing.
K8snot applicable to a backend pod — applies to a frontend Service/Ingress browsers hit directly.

13. Hardware/Sensors

hardware_sensors

Physical sensor telemetry — temperature, fan, PSU, voltage. Belongs to physical hardware, never to a virtual/OS CI.

Linuxnot applicable — linux-server is a VM/OS layer; sensors belong to esxi-host.
K8snot applicable to any K8s object — belongs to the bare-metal node, read via IPMI/Redfish.

B. Identity model — one CI, or nothing

Schema principle, verbatim: “Resolve every telemetry payload to exactly one CI via ordered match_rules; instance keys require their host (scope_parent) to resolve first.”

Why exactly one CI per payload, never zero, never many: ci_id is the join key every later stage relies on without re-deriving it. E4 Stores federates metrics/logs/traces into separate planes joined only by ci_id. E3's edges resolve both endpoints through ci_id. E9's upstream/downstream graph walk and E11's blast-radius rendering both key off it. If a payload could silently bind to zero or several CIs, every one of those downstream joins becomes ambiguous — a metric could attach to the wrong host, an edge could point nowhere, a verdict could blame the wrong entity. That's why the ambiguity_policy is absolute: “if >1 CI matches or none does, emit to unresolved bucket keyed by raw attributes; never silently mis-attach.” A wrong guess is worse than an admitted gap.

Scope levels — the granularity a match rule resolves to:

hostinterfacefilesystem diskcpuprocess serviceinstanceendpoint

Most keys (188 of 228 in the reference index) resolve at host scope in one lookup. The rest resolve at a finer scope and need their host resolved first (scope_parent): a disk-latency reading is scope filesystem/disk, but it can't bind until host.name binds. Skip that ordering and an instance metric silently flattens onto the host as if it were host-scoped — the exact failure mode use cases 6 and 7 (disk latency, disk usage) cannot tolerate.

Mapped onto a Kubernetes tenant, the same nine levels still apply — just populated by different telemetry:

host → node
Linux: host.name on linux-server. K8s: k8s.node.name on the Node object — the top-level scope_parent for everything scheduled onto it.
instance
Linux: a JVM instance, a cert serial, a mountpoint — one of several per host. K8s: one Pod/replica of a Deployment, keyed by k8s.pod.name + k8s.namespace.name, parent-resolved via k8s.node.name first.
filesystem / disk
Linux: a mount point (fs.mountpoint) or block device. K8s: a PersistentVolumeClaim mounted into a pod, backed by a PersistentVolume.
process / cpu
Linux: a PID, a CPU core. K8s: a container's process inside its PID namespace; its cgroup CPU share.
service / endpoint
Linux: a logical service spanning hosts, or an IP:port. K8s: a Service object (ClusterIP/DNS name) or an Ingress endpoint.

C. Relationship telemetry — the rulebook that builds edges

relationship_telemetry[] is not the graph itself — it's the generic, CI-taxonomy-agnostic rulebook E3 Topology runs against the identified telemetry stream to actually produce typed edges. For each of the 15 edge types it names the exact telemetry source, the signal fields matched, how direction is inferred, and what evidence tier the resulting edge gets. This is what turns a raw stream of metrics/logs/flows into app-runtime-jvm -[runs_on]-> linux-server with a receipt attached, rather than a hand-drawn diagram.

runs_on

software → host

A workload executes on a host.

Linuxnginx-web-server -[runs_on]-> linux-server, via ps/cgroup.
K8spod -[runs_on]-> node, via kubelet's .spec.nodeName.

hosted_on

vm → hypervisor

A virtual guest runs on a physical hypervisor.

Linuxlinux-vm -[hosted_on]-> esxi-host, via vCenter API.
K8snode -[hosted_on]-> ec2-instance, if nodes are cloud VMs.

member_of

member → group

Declared grouping/cluster membership.

Linuxesxi-host -[member_of]-> vsphere-cluster (declared, n/a confidence).
K8snode -[member_of]-> k8s-cluster, or pod -[member_of]-> replicaset.

part_of

child → parent

Structural containment, not co-location.

Linuxlocal-filesystem -[part_of]-> linux-server, via mount table.
K8scontainer -[part_of]-> pod, pod -[part_of]-> namespace.

depends_on

caller → callee

A functional/service-level dependency, inferred from traces or socket peers.

Linuxlinux-server -[depends_on]-> dns-service, via resolver config + query log.
K8scheckout-svc -[depends_on]-> payments-svc, via span peer.service.

uses

consumer → provider

Similar to depends_on, config- or trace-inferred consumption.

Linuxlinux-server -[uses]-> package-repo, via package-manager config.
K8spod -[uses]-> configmap/secret, mounted into the container spec.

mounts

host → storage

A host attaches a remote or block storage volume.

Linuxlinux-server -[mounts]-> nfs-share, via /proc/mounts.
K8spod -[mounts]-> persistentvolumeclaim.

connects_to

local port → remote chassis

Direct L2 physical/adjacent link.

Linuxlinux-server -[connects_to]-> access-switch, via LLDP/CDP.
K8snode -[connects_to]-> top-of-rack-switch — same LLDP, node is the host.

routes_through

host → L3 device

An L3 path device the host's traffic transits.

Linuxlinux-server -[routes_through]-> firewall, via routing table.
K8spod -[routes_through]-> egress-gateway/NAT-gateway.

communicates_with

initiator ↔ target

An observed network flow between two endpoints.

Linuxlinux-server ↔ backup-server, via flow/conntrack.
K8spod-a ↔ pod-b, via CNI flow / mesh sidecar.

authenticates_via

client → idp

An identity/auth dependency.

Linuxlinux-server -[authenticates_via]-> ldap-ad, via sssd/krb5 config.
K8sapiserver -[authenticates_via]-> oidc-provider.

monitored_by

ci → collector

Which collector observes this CI — the edge use case 5 exists for.

Linuxlinux-server -[monitored_by]-> monitoring-collector.
K8spod -[monitored_by]-> otel-collector-daemonset.

backed_up_by / backs

client ↔ backup-system

Inverse-direction pair describing a backup relationship.

Linuxlinux-server -[backed_up_by]-> backup-server.
K8spvc -[backed_up_by]-> velero-backup-target.

clustered_with

peer ↔ peer

Symmetric HA/cluster peer relationship.

Linuxlinux-server ↔ linux-server-peer, via corosync/VRRP.
K8spod ↔ pod in a StatefulSet, via headless-service peer discovery.

D. Which edge types the current 8 use cases actually walk

The schema defines 15 edge types, but the initial ObserveOps use-case catalog only exercises 11 of them (per the HLD's E7–E10 tables). This is what “scoped” means in your pipeline today: an edge type not listed below is fully supported by the schema but has no use case walking it yet.

UC-1/2

Error rate & Slowdown — call-chain walk

depends_onusescommunicates_withruns_on

Descend the call chain to the deepest still-symptomatic leaf; slowdown adds one upstream runs_on hop to check the hosting tier.

UC-3

Resource contention — noisy-neighbor path

runs_onhosted_onmember_of

Ascend from the symptomatic workload through its host to the hypervisor/cluster; descend back down to find every co-tenant.

UC-4

Availability — caller closure

depends_onusescommunicates_with

Whichever edge type connects a caller to the down entity, walked inbound and ordered by first_down_ts; redundancy metadata explains survivors.

UC-5

Monitoring unavailable — the edge that exists for this case

monitored_byconnects_toroutes_through

monitored_by fan-out from the collector is the merge key; connects_to/routes_through separate “collector broken” from “network partition.”

UC-6

Disk latency — storage chain

mountsdepends_onconnects_to

host → datastore → array → fabric switch, comparing latency tier by tier to find where it originates.

UC-7

Disk usage — filesystem instance

part_ofdepends_on

part_of names the host for context; depends_on reaches the backing datastore. Leaf is the mountpoint, not the host.

UC-8

connects_to

Host NIC → switch port chain; peer talkers resolved through flows_packets telemetry (a signal class, not an edge type) via the telemetry key index.

Not yet scoped by any of the 8 use cases: authenticates_via, backed_up_by, backs, clustered_with. The schema already supports auth-outage, backup-failure and HA-failover RCA — the use-case catalog just hasn't caught up. Worth planning for if those failure modes matter to your operators.

E. Root CI & root-relationship derivation

Root CI is simply the CI the worked example is anchored on — here, linux-server. root_relationship_derivation is written from that CI's own vantage point: for every other CI in the estate, direct (hop 1) or indirect (hop 2–3), it lists a ranked set of derivation methods — exact command/source, field, confidence, evidence type, rank — that tells E3 exactly how to discover that relationship by looking at or from the root CI itself, with no CMDB required. Indirect entries additionally carry a derivation_path: the literal hop-by-hop chain, so a multi-hop relationship doesn't need to be recomputed once found.

This differs from relationship_telemetry above: that's the generic rulebook for every edge type in the abstract; root_relationship_derivation is that rulebook applied, empirically, to one specific root CI, with real ranked commands (ss -tanp, ip route, lldpctl, iscsiadm -m session) rather than field names.

LinuxHop 1 downstream: app-runtime-jvm via runs_on, rank 1 = process/cgroup inventory (ps, systemd-cgls). Hop 2 indirect: app-hosting-svc, path linux-server → app-runtime-jvm → app-hosting-svc.
K8sHop 1 upstream from a Pod: k8s-node via runs_on, rank 1 = kubelet's .spec.nodeName. Hop 2 indirect: k8s-cluster, path pod → node → cluster via member_of — the direct K8s analogue of linux-vm → esxi-host → vsphere-cluster.

F. ci_telemetry — yes, it's the full composite object per CI

Each entry in ci_telemetry[] is everything the pipeline needs to know about one CI, in one place:

ci_id, ci_name, ci_type, ci_class, tier, instance_scope, monitored_via, kpi_catalog_ref identity: { match_rules[] } telemetry: { availability, performance, logs, traces, flows_packets, events, synthetic, config_topology, change_deployment, profiles, security_posture, rum, hardware_sensors } rca: { is_root_cause_candidate, blast_radius_impact, primary_health_signal, fault_signatures[] }

Three sub-objects, three jobs: identity answers “how do I bind an arriving payload to this CI.” telemetry answers “what does this CI emit, on which of the 13 signal classes, and how do I read it” — this is where the golden signals, log patterns and change sources from section A actually live, per CI. rca answers “when something's wrong here, what do I do about it” — the fault-signature playbook. One node = identify it, read it, diagnose it.

Linuxci_telemetry[0] = linux-server: identity keyed on host.name; telemetry.performance.key_metrics = system.cpu.utilization…; rca.fault_signatures = OOM-kill, CPU saturation, etc.
K8sA hypothetical k8s-pod entry: identity keyed on k8s.pod.name+k8s.namespace.name (composite, scope_parent = k8s.node.name); telemetry.events.key_events = BackOff/OOMKilled; rca.fault_signatures = CrashLoopBackOff, ImagePullBackOff. Same shape, different vocabulary — this is what “schema is the deliverable, not the CI list” means concretely.

G. The correlation line, explained

Full path: ci_telemetry[].telemetry.change_deployment.correlation. Full value in the file: “time-correlate change events against incident onset ('what changed in the 60m before')”.

It's not data — it's an instruction attached to the change_deployment signal class, telling E7/E10 how to use the change events it just collected (package installs, config drift, kernel updates, orchestrated runs): don't just log them, actively align their timestamps against the moment the fault started (first_down_ts / symptom onset), inside a trailing window — the file's own suggested default is 60 minutes. This is the classic “what changed right before this broke” RCA heuristic, formalized per-CI in the schema rather than left as a human habit. When a fault signature's timing lines up with a recent change on the same CI, that's strong corroborating evidence — it feeds the same evidence bundle as confirm_with_signals.

LinuxCPU/memory anomaly at 14:32; change_deployment shows a dnf update kernel transaction at 14:05 — 27 min before onset, inside the 60m window → flagged as a likely-cause candidate before logs are even read.
K8sPod enters CrashLoopBackOff at 09:10; the change-deployment equivalent — a Deployment rollout / new image tag applied at 09:02 — is 8 minutes before onset → the rollout is flagged as the likely root cause, mirroring the Linux package-update case exactly.

Grounded strictly in the ObserveOps HLD and the authored Linux-server illustration (observeops-ci-graph.html) — nothing speculative added beyond what those sources themselves flag as open, empty, or deferred.

Schema data gaps — fields shipped empty in the reference file

Data gap

Signal-class descriptions & default sources are blank

All 13 entries in telemetry_domains[] ship description: "" and default_sources: []. The schema declares the taxonomy but doesn't define it in machine-readable form — every definition on the Schema Reference tab had to be derived from HLD prose, not read off the JSON.

Impact: any UI/tooltip that wants to explain a signal class to an operator has nothing to render today; the class names alone aren't self-explanatory (what's the difference between events and logs? not stated anywhere machine-readable).

Data gap

No metric units or thresholds

Every entry in performance.key_metrics[] ships unit: "", use_tag: "", and empty correlate_with: []. This is the file's own stated known_gaps item, and the HLD's decision log #1/#2 confirm it's an open blocker for LLD-E6 — there's no KPI catalog file to reconcile against yet.

Impact: you cannot ship real E6 Detect thresholds from this file alone. Every metric name is shape-correct but unverified — treat as placeholder until reconciled against a real KPI catalog.

Data gap

primary_health_signal is blank

The node model reserves a single field for “the one metric that answers is this CI healthy,” and E6 is specified to read it directly — but it's empty on linux-server (and, from the sampled pattern, likely every CI).

Impact: a stage that's supposed to have a fast single-metric health check has to fall back to scanning key_metrics[] instead.

Data gap

Telemetry-key-index examples & fault relevance unfilled

All 228 entries in telemetry_key_index[] ship example: "" and fault_relevance: "". The lookup mechanism (key → CI) is complete; the descriptive metadata around it is not.

Impact: low urgency for E2 binding (which only needs the lookup), but blocks building operator-facing documentation or a self-describing API off this index.

Data gap

Some “not applicable” classes are unverified seeds

traces, synthetic, rum, and hardware_sensors on linux-server carry the reason “seed: not typical for this tier — verify.” The word “seed” flags these as auto-generated placeholders, not a confirmed engineering decision.

Impact: don't treat every applicable: false as final — the ones marked “seed” specifically need a human pass before you trust the absence.

Data gap

Vendor SNMP OIDs abbreviated to MIB names only

Also the file's own stated known_gaps item — e.g. BRIDGE-MIB dot1dTpFdbTable is named but not resolved to a numeric OID.

Impact: not actionable for a real SNMP collector without an OID lookup pass at build time.

Pipeline mechanism gaps — specified but not built (Design-level)

Not built

Edge evidence_type doesn't yet modulate confidence

The whole “moat” pitch is that provenance quality should shape trust — but HLD decision #3 explicitly defers wiring evidence_type into E9's ranking or E11's confidence cap. It's architecturally implied, not implemented.

Impact: if you ship confidence scores today, they aren't actually weighted by how the edge was discovered yet — the gap between the schema's promise and current wiring is real.

Not built

The live E3 graph builder doesn't exist

The HLD's own honesty note: the schema is Grounded as an artifact (it exists, fully populated) but was authored, not emitted by a running E3. “E3 discovers these edges live from the telemetry stream at the stated refresh cadence” is Design-level.

Impact: don't assume the graph self-discovers or self-refreshes today — that continuous derivation loop is specified, not shipped.

Not built

Declared-edge staleness decay has no job behind it

The 7-day soft-stale / 30-day hard-downgrade rule (decision #4) is a proposed default. E5 Maintain, which would enforce it, is flagged Design-level overall — “no dedicated lab exercises it.”

Impact: a declared edge like esxi-host -[member_of]-> vsphere-cluster will sit in the graph, silently unrevalidated, until this job is actually built.

Not built

Operator feedback loop into E3 is fully specified, zero implementation

GraphFeedbackEvent (confirm/reject → rolling per-edge trust score) is designed in HLD §3.5, decision #9 — but needs an ADR before LLD-E3 even picks it up.

Impact: the graph cannot self-correct from analyst verdicts yet; every VerdictCard confirm/reject is currently discarded rather than fed back.

Not built

UC-7/UC-8 attribution deferred (decision #8)

“Which process is filling the disk” (UC-7 writer attribution) and “which peer is saturating the link” (UC-8 top-talker attribution) are explicitly out of v1 scope. v1 ships at “disk is full” / “link is saturated” granularity only.

Impact: if operators expect the verdict to name the offending process or peer, not just the symptomatic resource, that's an acknowledged v2 gap.

Not built

Cross-class escalation annotation mechanism is proposed, not implemented

UC-7 (disk usage → availability-shaped) and UC-8 (throughput → slowdown/availability-shaped) escalation is decided as “annotate, don't reclassify” (decision #6) — but the annotation mechanism itself has no implementation yet.

Normalization at scale (E2 Identity)

E2P0 · foundational

Goal

Prove E2's identity resolution (match_rules + telemetry_key_index lookup) holds at real multi-tenant ingest volume, not just the 33-CI / 228-key reference scale.

Why this, now

POC-3

Baseline, pattern & anomaly-score substrate (E1–E5)

E1–E5P0 · foundational

Goal

Build the continuous statistical layer under E6 — per-CI, per-metric baselines, pattern classification, and a running anomaly score — so E6 Detect only has to threshold-check a pre-computed score, never compute statistics inline.

Why this, now

Decision log #1/#2 say metric names are placeholder and units/thresholds are unreconciled, explicitly blocking LLD-E6. This POC (paired with POC-6) is what actually unblocks it.

Approach

  • Classify each telemetry key's pattern at onboarding (stationary / diurnal / weekly-seasonal / trending) via autocorrelation or STL-decomposition, and pick the baseline method per type: EWMA for noisy stationary metrics (CPU, memory), rolling percentile bands (p50/p95/p99) for latency-style metrics, seasonal-STL residual for cyclic ones (request rate).
  • Compute a continuous robust deviation score (MAD-based or z-score off the chosen baseline) per metric, rather than a hard threshold — E6 then just compares this score against a Detect-class-specific bar.
  • Persist baseline state (not raw metrics) in a compact rollup store separate from hot-tier retention — EFS hot tier's 2–3 day window is shorter than the 14–30 days most seasonal baselines need. This is a real architecture decision, not a footnote.
  • Wire this as an E5 Maintain responsibility (“a running property of the fabric, not a batch pass”), matching the HLD's own framing rather than bolting on a separate offline job.

Deliverable / exit criteria

  • Coverage: every reference telemetry key (228) plus the K8s equivalents from POC-7 has a live (pattern_type, baseline, anomaly_score) triple updating at ≤1 min staleness.
  • Detection: on 10 injected synthetic faults (5 Linux, 5 K8s), each matched to a known fault_signature, the anomaly score crosses the Detect-class bar within 2 minutes of onset for ≥90% of them — the same top-1 90% bar the HLD sets for E9.
  • False positives: over 7 days of unmodified baseline traffic, fewer than 1 false trigger per CI per week.
  • Durability: baseline state for a 30-day seasonal window survives a hot-tier eviction (EFS's 2–3 day retention) without losing continuity.

Example — what “done” looks like

Linuxsystem.cpu.utilization on linux-server is classified stationary/noisy → EWMA baseline; injecting a synthetic CPU-saturation fault trips the anomaly score within the 2-minute budget.
K8shttp.server.request.duration p95 on a Service is classified diurnal → STL-seasonal baseline; a latency injection during a normally-quiet overnight window is still caught, and the same absolute latency during the normal daytime peak does not false-positive.

POC-4

E6–E8 statistics & graph algorithms to assemble the window

E6–E8P0

Goal

Decide and prove the concrete math behind Detect → Curate → Scope — turning per-CI anomaly scores into one bounded, correlated WorkingSet ready for E9.

Why this, now

This is the seam the HLD leaves most implicit — it names each stage's IN/OUT but not the algorithm. Get it wrong and E9 either drowns in noise (under-merged) or loses the real cause (over-merged).

Approach

  • E6 Detect: threshold the POC-3 anomaly score against a Detect-class bar. Use CUSUM (cumulative sum control chart) to tell a sustained shift from a noise spike; for rate-based signals (error rate, request rate) use a Poisson/binomial rate test instead of a z-score — count data violates the Gaussian assumption a z-score needs.
  • E7 Curate: model active signals as nodes in a “signals graph” — edges = E3 adjacency AND temporal overlap within a correlation window — and run connected-components (union-find) to merge. Rank the seed within a component by hop-distance/upstream-ness. Deterministic and auditable, no ML needed.
  • E8 Scope: bounded BFS from the seed, capped by the decision-#5 hop-depth/candidate table. Calibrate the correlation window itself empirically — mine historical or fault-injected incidents for a per-edge-type propagation-delay distribution and set the window to its 95th percentile, instead of a flat constant like the schema's own 60-minute default.
  • Keep E6–E8 classical statistics + deterministic graph algorithms, not ML — reserve ML for genuinely ambiguous multi-hop ranking in E9–E11 (POC-5). This maximizes explainability for a product whose core promise is an auditable verdict.

Deliverable / exit criteria

  • Merge accuracy: on a labeled set of ≥20 synthetic multi-signal scenarios (mixing Linux and K8s), E7's merge-or-not decision hits ≥95% precision/recall against the labeled ground truth.
  • No over-merge: graph-adjacent signals within the correlation window merge into one CaseSeed; signals that are not graph-adjacent must not merge even if temporally coincident — an explicit negative test case.
  • Bounded scope: WorkingSet size stays within the decision-#5 caps for every Detect class, on both the Linux and K8s topologies.
  • Calibrated window: propagation-delay distribution measured from ≥20 fault-injection replays per edge type; the 95th percentile is what's used as the correlation window, not the schema's flat 60-minute default.

Example — what “done” looks like

Linuxsystem.cpu.utilization (host), a GC pause (app-runtime-jvm) and latency on nginx-web-server fire within the correlation window, all connected via runs_on — E7 merges all three into one CaseSeed rooted at linux-server, not three separate cases.
K8sCPU pressure on a Pod and Ready-flapping on a sibling Pod on the same Node merge into one CaseSeed via runs_on; a latency signal on an unrelated Service on a different Node does not merge, even in the same minute.

POC-5

ML / agentic AI for E9–E11, constrained for determinism

E9–E11P1

Goal

Decide precisely where ML or an agentic Claude-based reasoner earns its place in Localize/Identify/Package — and where it must not, so the no-false-blame gate and confidence semantics stay deterministic.

Why this, now

The HLD's own leaf rules (deepest error leaf, longest self-time leaf, contended entity even with a negative symptom, first-down entity, coverage-gap entity) are already deterministic per-class rules. The open question is only what to do with genuine ambiguity, and how to narrate a verdict without letting a model freelance on it.

Approach

  • E9 Localize: keep the deterministic leaf rule primary. Where the graph offers tied or corroborating-only candidates, add a lightweight learned ranker (e.g. gradient-boosted, trained on historical GraphFeedbackEvent confirm/reject outcomes from decision #9) as a tie-breaker and confidence modifier — never an override.
  • E10 Identify: the strongest fit for an agentic reasoner — given a structured EvidenceBundle, have it produce the corroboration narrative and evidentiary-tier judgment, but constrain it to choosing among the CI's own pre-computed fault_signatures[] rather than freely hypothesizing a cause. Grounded generation, not open diagnosis.
  • E11 Package: LLM-generated VerdictCard prose is fine; the confidence number must be a hard post-generation clamp — “cannot exceed the weakest evidence_type traversed” (the HLD's own universal E11 rule) enforced in code, never left to model discretion.
  • The operator feedback loop (decision #9) is the real candidate for a standing agent: a scheduled job that reviews the trailing window of confirm/reject events, updates per-edge trust scores, and raises signature-quality-queue tickets for human review — a natural fit for your platform's own agentic-AI-for-autonomous-IT-ops goal.
  • Run a bake-off before committing: the same 5–10 fault scenarios through pure-rule E9–E11 vs. ML/agent-assisted, measuring agreement rate and operator-rated narrative usefulness.

Deliverable / exit criteria

  • Accuracy floor: on a held-out bake-off set (mixed Linux/K8s), both the rule-only and ML/agent-assisted paths hit the HLD's own top-1 ≥90% bar; agent-assisted must not score lower than rule-only on any scenario.
  • Clamp holds: in 100% of bake-off runs, the agent-assisted path's stated confidence never exceeds what the rule-only path's weakest traversed evidence_type would allow — a scripted regression check, not a spot check.
  • Grounded narrative: in an audit of ≥30 generated E10 corroboration narratives, 100% reference only fault_signatures/log key_patterns actually present in that verdict's EvidenceBundle — zero fabricated causes.
  • Feedback loop: after exactly 3 reject events on a corroborating edge (decision #9's minimum sample size), its confidence downgrades one notch automatically — verified in a scripted test.

Example — what “done” looks like

LinuxThe HLD's own UC-3 case — JVM slow, linux-server looks healthy, esxi-host underneath is contended. Rule-based E9 still picks esxi-host as leaf even with the ranker enabled; the ranker only activates as a tie-breaker when two co-tenant hosts show comparably borderline saturation.
K8sA Pod in CrashLoopBackOff on a Node where a sibling Pod was OOMKilled. E10 corroborates via the container's OOMKilled status reason plus a change-deployment correlation hit; if the path crossed a declared Node→cluster edge, the VerdictCard confidence is clamped and cannot read “high,” regardless of how clean the metric evidence looks.
