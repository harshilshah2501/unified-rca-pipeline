How hot and cold are kept

HOT · live

In the GraphWriter / map_vortex process

Current estate for walks: node/edge Arrays (and adjacency when Phase C lands).

  • Grows from admitted stream lines
  • Mutated in place until the next publish
  • After restart: rebuilt by load_map from cold
  • Not a second copy of S3 opened per hop
COLD · checkpoint

Immutable objects on Dest (S3 / path)

One generation = present map frozen at publish time.

  • nodes/part-*.vortex + edges/part-*.vortex
  • manifest.json lists the parts
  • latest.json points at the generation
  • Never patch an old .vortex — write a new version

Pillar B map/ is present status, not the ObserveOps history/ sketch room. Snapshot versions are checkpoints of that present map for load/rebuild — not an event diary.

Why Arrow sits in the middle

Arrow

In-memory columnar spreadsheet (RecordBatch). Same columns as the Motadata lock. Build and scan language.

Vortex

On-disk / object packing: compression, zones, postscript. Optimized for prune + selective read from S3.

Together

We build Arrow; SpiralDB’s bridge turns it into a .vortex file. On load, Vortex materializes back toward Arrow for walks.

Who writes what

ObserveOps / map_vortex

Admit, hot upsert, Arrow schema + RecordBatch, Dest paths, manifest / latest.

SpiralDB vortex crate

from_arrow_record_batch → write_options().write → VTXF segments + layout + postscript.

Not our job

Hand-editing Vortex footers, or treating .arrow demo twins as Motadata cold SoT.
