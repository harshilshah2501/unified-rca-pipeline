1 · What is an exemplar?

An exemplar (in the OpenTelemetry / GCP Monitoring sense) is a small pointer stored beside a histogram bin — usually one trace_id or request id — so an operator can open one real request that landed in a hot latency range after Detect has already fired. In our sketch.v1 row it is an optional parallel array buckets.exemplars[], aligned index-for-index with buckets.counts[].

What an exemplar is

A bookmark captured at E4 (platform sketch writer) while Pillar A still sees each resolved metric_sample and updates bins. One id per bin (policy: first in bin, slowest in bin, etc.). Stored in history/ on the flushed sketch.v1 row.

What an exemplar is not

Not a metric raw lake. Not every request in the bin. Not a substitute for T-Digest, buckets, or baseline. Not required for E6 Detect (door C). Not reverse-engineered from counts[] after flush.

One-line definition: exemplars answer “which request should I open first?” after buckets have already answered “which range is hot?” — without keeping every resolved metric_sample in history/. On the RED pattern, that question applies almost only to Duration (latency), not Rate or Errors counters.

2 · RED metrics — Rate · Errors · Duration

RED is the usual service-health lens for request-driven workloads (HTTP APIs, gRPC, queue consumers). Three questions: how busy, how broken, how slow. RED does not replace topology RCA — it tells Detect and operators where to look first. Each letter is usually one or more time series per service (often per route), not a single magic metric name.

E2 stamps identity (ci_id, resolved) and passes labels — it does not build histogram bins or exemplars. E4 aggregates resolved metric_sample lines into one sketch row. Exemplars copy a trace_id label during that pass; the operator later resolves it in the trace store, not from metric raw in history/. See how trace_id resolves.

Where in the pipeline — E4 Collect path, not E2 Identity

E2 Identity (look-up / bind) stamps tenant + ci_id and passes labels through — including trace_id if the metric_sample already carries it. E2 does not maintain histogram bins or write exemplars[]; that requires bucket counts, which is sketch-writer work.

E4 Pillar A sketch writer (platform, after E2) aggregates resolved metric_sample lines into one sketch.v1 row: T-Digest, buckets, baseline, and optionally exemplars. The bookmark is chosen here — while the writer increments counts[] — then metric raw for that window is discarded.

Edge / shift-left (optional, before E1 Collect) may shape volume or attach tags earlier, but our locked contract places exemplars on the platform sketch row (G42). A future edge histogram with exemplars would be a different aggregation layer — not E2 Identity.

3 · Four mechanisms — digest, buckets, baseline, exemplars

Pillar A’s sketch.v1 row can hold four complementary structures about one metric window. The first three are the core Detect + investigation stack; exemplars are an optional accelerator on top.

T-Digest

Question: how bad as a percentile this window?
Input: numeric value from each resolved metric_sample (not T-Digest output).
Output: mergeable p50 / p95 / p99.
E6 Detect: yes — current p95.

Buckets

Question: where is the mass in fixed ranges?
Input: same metric_sample values as digest (parallel readout).
Output: bounds[] + counts[].
E6 Detect: no (primary path). After fire: yes — hot bin.

Seasonal baseline

Question: what is normal for this hour-of-week?
Input: past windows with same season_key (e.g. Thu-09:00).
Output: expected_p95 (and p50/p99).
E6 Detect: yes — expected p95.

Exemplars (optional)

Question: which single request in a hot bin?
Input: value + trace_id label from each metric_sample at write time.
Output: one id per bin in exemplars[].
E6 Detect: no. After fire: yes — open trace.

MechanismDetect (E6 door C)After DetectCan drop metric raw?
T-DigestCurrent p95 vs baselineCorroboration, merge across windowsYes — digest is the kept aggregate
BucketsNot in primary ratioHot range, heatmap, rules on bin countsYes — counts are the kept aggregate
BaselineExpected p95 for season_keyContext (“usually 173 ms at Thu 09:00”)Yes — built from past sketch rows
ExemplarsNot usedClick-through to one trace in hot binYes — id captured before discard

Digest + baseline are enough to fire Detect: current_p95 / expected_p95 > threshold (walkthrough: 455 / 173 = 2.64×). Buckets tell you the abnormal mass sits in [200, 500) ms with n = 2836. Exemplars add trace-000001 on that bin so you do not have to hunt traces manually. None of the four replaces another; exemplars are the only one that is optional in v1 schema. On RED dashboards, only Duration uses this quartet; Rate and Errors use counter paths.

4 · OpenTelemetry vs ObserveOps — our take

Both ecosystems share one idea: an exemplar is a write-time pointer from an aggregate (histogram bin or sketch bin) to one underlying measurement — usually so an operator opens a trace by trace_id. Neither keeps every metric sample forever. The [OpenTelemetry Metrics SDK](https://opentelemetry.io/docs/specs/otel/metrics/sdk/#exemplar) calls exemplars “example data points for aggregated data”; our contract matches the drill-down goal but differs on pipeline stage, storage, and Detect.

5 · With vs without exemplars — scenarios and justification

The existing digest + buckets + baseline system is complete for Detect and for knowing where latency regressed. Exemplars only change how fast an operator reaches one concrete request — not whether Detect fires.

Same incident — operator path comparison

Scenario: checkout-api · request.latency_ms · Thursday 09:00 · p95 = 455 ms vs expected 173 ms (2.64×).

Without exemplars (digest + buckets + baseline only)

  1. E6 Detect fires — digest p95 vs seasonal baseline. Signal: SLOWDOWN on checkout-api.
  2. Investigate “where” — open heatmap / bucket view. Hot bin: [200, 500) ms, n = 2836.
  3. Investigate “which” — open trace or log explorer. Filter service, time window, sort by duration.
  4. Manually hunt — scan slow traces until one matches the hot range. Works; slower; more triage drift.

Justification to skip exemplars in v1: Detect and localization still work; tracing may be sparse; team may prefer logs + topology.

With exemplars (same sketch row, optional array)

  1. E6 Detect fires — identical math. Exemplars do not change fire / no-fire.
  2. Investigate “where” — same hot bin [200, 500) ms from buckets.
  3. Investigate “which” — UI reads exemplars[bin3] = "trace-000001" from the sketch.
  4. One click — open that trace in APM / OTel backend. See e.g. payments-db span at 420 ms immediately.

Justification to enable: high-traffic services, trace-first debugging, repeated “which request?” bottleneck after SLOWDOWN fires.

Why exemplars do not replace digest + buckets + baseline: you cannot compute p95 vs season from a trace_id, and you cannot know the hot range from a trace alone. Exemplars assume the sketch already proved abnormality (digest + baseline) and already located mass (buckets). They only shorten the last hop to a trace product.

6 · How write-time capture works

Terminology — what “sample” means on this page: A sample is one resolved metric_sample ingest line — one measurement event with a numeric value (for example 420 ms) and optional labels (for example trace_id). It is input to the E4 sketch writer, not output from T-Digest. T-Digest, buckets, and exemplars are three parallel summaries built from the same metric_sample while the writer still holds it in memory. After flush, individual lines are discarded; only aggregates land in sketch.v1.

The counter-question: “counts are aggregate — how does trace_id appear if we discard metric raw?” Answer: the writer stores the id while each metric_sample is still visible, in a parallel side table — not by decoding counts[] later.

Key insight: bucket counts[] are pure aggregates — you cannot reverse a trace_id from “2,836 metric_samples in [200,500)”. The writer remembers one id while each metric_sample is still visible, stores it beside the bin, then discards the in-window stream. Investigation uses sketch → stored trace_id → trace/APM store, not histogram → inferred id.

What the histogram stores

Only how many metric_sample values fell in each fixed range. No per-request ids inside counts[].

counts: [2, 8, 10, 2836, 2, 1] bounds: [0, 50, 100, 200, 500, 1000, 2000]

What the exemplar stores (optional)

A parallel side table filled during E4 — typically one trace_id per bin (policy: first in bin, slowest, etc.).

exemplars: [null, null, null, "trace-000001", "trace-000042", null]
Per incoming metric_sample (while E4 writer still sees it): metric_sample { value: 420 ms, labels: { trace_id: "trace-000001" } } ├─► T-Digest.update(420) ← consumes value; updates centroids (not a sample) ├─► buckets[200-500) count += 1 ← consumes value; increments count └─► exemplars[200-500) = "trace-000001" (only if slot empty — first-in-bin policy) After flush → sketch.v1 in history/ · in-window metric_sample list discarded Later → Detect on digest vs baseline · click exemplar → trace store (not history/)

7 · Step by step — metric_sample stream → sketch row

Four animated steps — one focus per tab. Each step shows how E4 aggregates resolved metric_sample lines (input), not T-Digest output. Use arrow keys on tabs to step through.

Step 0 — metric_samples in

The sketch writer receives resolved metric_sample lines for one closed window. These are input events (one measurement each), not T-Digest centroids. Lines may include a trace_id label from upstream APM. Nothing is persisted yet — the writer aggregates in memory.

Step 1 — parallel update

Every metric_sample updates digest, bucket count, and (optionally) the exemplar slot in one pass — same input, three different summaries. Digest and buckets answer different questions from the same value. Exemplar stores one trace_id beside the hot bin — not inside counts[].

Step 2 — baseline

Door C Detect compares digest p95 to the seasonal expected p95. Buckets and exemplars are not part of the fire decision — they matter after the Signal.

Step 4 — flush

Watch the cycle: aggregates compress into one sketch.v1 row (digest, counts, exemplars, baseline). The in-window metric_sample stream is discarded — only the exemplar string survives inside the row, as a lookup key to the trace store, not as metric raw.

The exemplar string on the sketch row is not metric raw and not a row key inside history/. It is a foreign key into the trace / APM product that already stored that request when it ran. Resolution is a cross-product lookup, not a replay from the discarded metric_sample stream.

Ready reply — “How is trace-000001 resolved?”

We store one id per bin on the sketch row (default: first in bin). After Detect, the UI reads that string from exemplars[] and calls the trace store with GET trace("trace-000001") — the same id APM already indexed when the request ran. We do not reconstruct the trace from history/ metric raw; the exemplar is only a lookup key.

10 · Two stores — metric raw vs trace product

Do not collapse these. Exemplars do not pull individual metric_sample lines back out of the histogram. They point at a trace / span store (APM, Grail, OTel backend) with its own retention.

Animated tabs — write-time capture vs post-Detect investigation path.

Write time — two stores

Resolved metric_sample lines compress into history/sketch.v1. The exemplar stores a trace_id pointer to a separate trace/APM product. Do not collapse in-window metric discard with trace retention — they are different products.

Investigation path

After E6 fires, buckets show where mass sits. Exemplars jump to which request via the trace store. Without exemplars the first three steps still work — the operator hunts traces manually.

11 · Common confusions

“trace-000001” is not a pointer into metric raw in history/

You are right: after flush, history/ does not keep the original metric_sample line for 420 ms. The exemplar id is also not a row key back into a metric raw lake. It is a lookup key into a different product — the trace / span store (Datadog APM, Dynatrace, OTel backend, etc.) that already captured that request when it ran.

WHEN THE REQUEST HAPPENED (before E4 flush) APM / OTel already stored the full trace under trace_id = "trace-000001" (spans, timings, errors, service names — separate retention) WHEN E4 WRITES THE SKETCH metric_sample { value: 380 ms, trace_id: "trace-000001" } ← writer sees this once exemplars[bin [200,500)] = "trace-000001" ← copies the id beside the bin metric_sample stream discarded ← 380 ms line not kept in history/ LATER — OPERATOR CLICKS THE EXEMPLAR UI: GET trace("trace-000001") on trace store ← NOT a read from history/ → flamegraph / span tree for that one request → logs joined by same trace_id (if your APM supports it) What you get back: one real request path — not the full list of 2,836 requests in that bin.
Where did trace-000001 come from? Upstream instrumentation put it on the metric_sample label when the request was measured. E4 only remembers that id while processing the line. “First in bin” means the first request that landed in [200,500) during that window — a bookmark, not a guarantee it was the slowest. If the trace aged out of APM, the link is dead even though the exemplar string remains on the sketch row.

Low traffic — can we use exemplars alone (skip T-Digest + buckets + baseline)?

No — not in ObserveOps Pillar A / E6 door C. Exemplars and the sketch aggregates do different jobs:

QuestionWho answers itExemplars alone?
“Is latency abnormal for this hour-of-week?”T-Digest + baseline → E6 DetectNo — a trace id does not tell you p95 vs season
“Which latency range is hot?”Buckets → heatmap / rulesNo — one id does not describe mass across bins
“Open one request in that hot range”Exemplar → trace storeOnly after the first two are answered

In low-traffic services the tradeoff flips the other way (G29): manual trace or log search is cheap, so you often skip exemplars — not replace digest + baseline with exemplars. You might keep raw metrics longer in a hot tier, or debug from traces directly, but that is a different storage choice — not “exemplars instead of sketch.v1.”

High traffic (exemplars worth it)

Thousands of requests per window → hunting traces manually after Detect is slow → store one trace_id per hot bin.

Low traffic (exemplars often skipped)

Tens of requests per window → you can open traces or logs without a bookmark → still keep digest + baseline for Detect; skip optional exemplars[].

12 · Pipeline stages — who needs what

Two tabs — E6 Detect (digest + baseline only) vs investigation (buckets + exemplars).

E6 Detect — without exemplars

Detect fires from digest + baseline alone. Buckets and exemplars are greyed out — they do not change fire/no-fire. This is the complete Detect path even when exemplars are disabled.

Investigate — where exemplars help

After Detect, buckets show the hot range. Exemplars (if enabled) store one trace_id for click-through. Without exemplars you still have buckets — but manual trace search replaces the last hop.

At E4 write, all four structures can be built from the same metric_sample stream (exemplars optional). At E6 Detect, only digest + baseline participate in door C. At E8 Scope / E10 Identify and operator investigation, buckets locate the range and exemplars (if present) jump to a trace. See G41 for why E6 needs no graph edges.

15 · Cheat sheet and further reading

Same data?

Digest + buckets: same window’s metric_sample values.
Baseline: past season_key windows.
Exemplars: one trace_id per bin policy, captured at write.

Substitutes?

Exemplars do not replace digest, baseline, or buckets.
Detect does not need exemplars.
Exemplars are post-Detect acceleration (G29).

Not the same as…

Detect on a 1% subsampled metric stream (different product).
An event / execution graph.
Re-reading metric raw from S3 after flush.
A full trace archive inside history/.

We store one trace_id per bin (default: first in bin). After Detect, the UI reads that id from exemplars[] and resolves it via the trace store (GET trace(...)) — not from metric raw in history/. We see each metric_sample once at E4, update digest and buckets, copy the label onto the hot bin, then discard the stream. Detect still runs on digest + baseline only; exemplars are optional post-Detect speed.
