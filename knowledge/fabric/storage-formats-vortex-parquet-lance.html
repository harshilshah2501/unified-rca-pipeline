Vortex · Parquet · Lance — what each is for

Three names that often appear together around S3 object storage — but they are not three peer file extensions. Vortex is Motadata’s hot analytical product (engine + query layer). Parquet and Lance are open columnar encodings — files or tables that can sit on S3. ObserveOps locks the logical row first (sketch.v1, graph_edge.v1); physical encoding comes after Signed field tables. Companion: Vortex + S3 interaction (temperature + query path) · normative map I/O MAP_WRITE_READ_RECORD.md §6 (.vortex parts, VTXF postscript, ObserveOps manifest.json) · owner notes vortex_engineering_mystery_revised_v2.pdf.

One line each

Vortex = query fast (hot index + engine; may read S3 underneath).
Parquet = remember cheaply (immutable columnar files; scan-friendly cold history).
Lance = object-native columnar tables (random access + versioning on S3; optional future encoding).

Not three formats on the same shelf

Compare at a glance

Product · hot

Vortex

Motadata-shaped analytical engine. Holds or indexes recent map/ + history/ rows. Serves interactive lookup and the diagnose query layer. May federate scans over cold S3.

Format · cold

Parquet

Open columnar file format (.parquet). Industry default for data lakes. Best for append-only history, batch analytics, and ETL scans over partitions.

Format · cold / hybrid

Lance

Open columnar table format (Lance). Built for object storage: fragments, cheap random access, snapshots. Common in ML / vector / modern lakehouse stacks — optional in our Gate B profile.

How each one works (animated)

Vortex — interactive engine, not a file suffix

Writers land logical rows after E3/E4. Vortex keeps a hot working set and exposes the query layer Retrieval uses. When a key is missing from hot storage, the engine may federate a scan over cold S3 objects — but the diagnose path still goes through Vortex, not ad-hoc S3 dumps.

E3/E4 writers → Vortex (hot) → age-out → S3 (Parquet/Lance) Retrieval → Vortex query layer → WorkingSet → E9/E10

Parquet — immutable cold history

Each closed window becomes (or appends to) a partitioned object on S3. Columns are stored together, so analytics reads only the fields it needs. ObserveOps teaching paths use Hive-style prefixes (tenant=…/metric_id=…/date=…). Best when queries are batch scans over time ranges — backfill, retention, federated cold read through Vortex.

sketch.v1 row → Parquet writer → s3://…/date=…/part-NNN.parquet Query (via Vortex): partition filter → column projection → rows

Lance — object-native columnar table

Lance stores a dataset as many fragment files plus a manifest. Writes append new fragments; readers can do point lookups and version snapshots efficiently on S3 — useful when cold tier still needs selective reads without loading whole Parquet partitions. Not required by current PoC contracts; listed here because teams often compare it next to Parquet when designing the cold lake.

append fragment → update manifest → readers pin a version Optional: Vortex federates Lance dataset same as Parquet partitions

When Parquet fits

Aged sketch windows, compliance retention, batch rebuild into Vortex, cheap storage per GB. Scan by date= / metric_id= partition.

When Lance fits

Selective cold reads, dataset versioning, ML feature stores beside observability, random access without full partition scan. Product choice — not locked in PoC.
