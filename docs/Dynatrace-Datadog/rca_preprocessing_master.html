01

The problem, condensed

Full detail lives in the original brainstorm doc — this is the load-bearing summary.

Given noisy, high-volume, multi-modal telemetry and a shifting estate, automatically (or assistively) answer what is wrong, where the fault is, and — when justified — why, with an evidence trail an SRE can trust.

The real systems problem isn't "store everything." It's: create an entity-keyed, time-aligned store, then per-incident tailor a small AI-ready working set (seed + neighborhood + corridor) that Localize/Identify can reason over. Five jobs, in order: Ingest → Detect → Localize → Identify → Verify. This document covers everything up to and including Detect — the pre-processing puzzle, before RCA proper begins.

✓ VERIFIED THIS SESSION
  • Dynatrace: current docs describe deterministic, causation-based analysis using Grail + Smartscape, now branded "Dynatrace Intelligence" with Davis AI as the underlying engine and Davis CoPilot as the newer generative layer.
  • Datadog: Watchdog RCA is documented as a bounded classifier with exactly four root-cause types (version changes, traffic increases, AWS instance failures, disk space exhaustion) — and explicitly never classifies latency/error increases themselves as root cause. This is narrower and more rule-based than "statistical correlation ranking."
  • Datadog also shipped Bits Investigation (announced DASH 2025, GA since Dec 2025) — a separate, more open-ended agentic SRE investigator, distinct from Watchdog RCA. Worth adding to the vendor comparison doc as its own row, not folded into Watchdog.
✗ NOT CONFIRMED — from the Gemini-authored spec
  • A named "Two-Stage Correlation Engine" (Signal Correlation vs. Causal Correlation) presented as Dynatrace's actual internal architecture — I found no Dynatrace documentation using this framing. It's a plausible pattern (and arguably a reasonable design for our own Seed/Tailor stage), but shouldn't be cited as "how Dynatrace does it."
  • Exact ingest attribute names dt.event.suppress_problem, dt.event.is_rootcause_relevant, dt.event.allow_davis_merge — I could not independently confirm these specific field names in current docs. Treat as unconfirmed until checked directly against the Dynatrace ingest attribute reference.
  • A specific "5-stage OpenPipeline" breakdown (Validation → Masking → Extraction → Davis Readiness → Bucket Routing) and the term "Distilled Evidence Package" — OpenPipeline itself is real and verified, but this particular staged breakdown and terminology aren't things I found in Dynatrace's own docs. Likely Gemini's own synthesis, not a citation.
  • The file also wired a live call to a Gemini TTS/generation API with a blank key — this will not function as a static artifact and was dropped from this consolidation.
