G. Glossary (read this first)

Terms used throughout. Bold = used constantly.

G.1 Two clocks (structural)

TermMeaning
Clock AThe continuous platform / ingest / lake timeline: collect telemetry, normalize it, keep topology fresh, store/retain, and — when an incident starts — tailor a small working set. Runs all the time, whether or not anyone is debugging.
Clock BThe per-incident diagnosis timeline: after Tailor, Localize → Identify → Verify for that case. Starts and ends with an incident.
Why “clock”?Metaphor only: two different cadences. Do not mix “we need a better lake” (Clock A) with “our Localize missed the root” (Clock B) in the same discussion without saying which clock you mean.

One-line: Clock A prepares joinable data; Clock B reasons about one fault.

G.2 RCA jobs (Clock B)

TermMeaning
IngestMake signals joinable by identity + time (usually Clock A; listed first in the end-to-end chain).
DetectDecide that something is wrong now, and where pain shows. Emits anomalies / alerts.
Symptom seedThe (CI, signal, time) where Localize starts. Usually a symptom, not the root cause.
LocalizeFind which CI / service is the fault region (Step 1 “where”).
IdentifyName the kind of failure (signature / fault class), and optionally the execution path (Step 2).
VerifyHow strongly we may claim cause (evidence depth / confidence tiers — not marketing “causal”).
Step 1Market shorthand ≈ Detect → Localize (“where”). Vendors automate this relatively well.
Step 2Market shorthand ≈ Identify (+ Verify) (“what happened there”). Deep path-diff automation is still thin industry-wide. See two-step-rca-white-space.md.

1. What is the problem?

1.1 One-sentence problem

Given noisy, high-volume, multi-modal telemetry and a shifting estate, automatically (or assistively) answer: what is wrong, where is the fault, and—when justified—why, with an evidence trail an SRE can trust.

1.2 End-to-end jobs

Ingest→ Detect→ Localize→ Identify→ Verify
JobPlain questionFailure mode if skippedTypical clock
IngestCan we join signals by identity + time?Orphan metrics/logs; no walkMostly A
DetectIs something wrong now, and where does pain show?No case start / wrong seedA (opens case; Curate → seed)
LocalizeWhich CI / service is the fault region?Blame the loud symptom appB
IdentifyWhat kind of failure (and optionally which path)?“Host X bad” with no actionable classB
VerifyHow strongly may we claim cause?Marketing “causal” without evidence depthB

Market shorthand:

  • Step 1 “where” ≈ Detect → Localize.
  • Step 2 “what happened there” ≈ Identify (+ Verify).

1.3 Why a “bigger lake” alone is not the solution

Raw production data is:

  • Huge — metrics × hosts × minutes; log lines; sampled spans
  • Heterogeneous — infra vs app vs change events
  • Non-stationary — deploys change topology
  • Identity-unstable — pods churn; monitors rename

So the systems problem is not “store everything.” It is:

Create an entity-keyed, time-aligned store; then, per incident, tailor a small working set (seed + neighborhood + corridor) that Localize/Identify can reason over.

Datadog/Dynatrace-class products optimize for that operationally. Any serious RCA stack needs: normalized streams + scoped working sets, not full-retention diagnosis.

Ingest is not RCA. Collecting and storing well does not localize a fault. Localizing well does not invent missing topology.

1. Collect

InputRaw telemetry from the estate: Prometheus scrapes, syslog, traps, OTel spans/logs, agent metrics, change/deploy feeds, vendor APIs, replay files
ProcessAgents / collectors / Vector sources pull or receive bytes; optional light filter (drop noise, TLS terminate). No RCA yet
OutputRaw (or lightly framed) events on a bus / file / Vector internal stream — still vendor-shaped, often without stable ci_id

2. Normalize

InputCollect output (raw / semi-raw events)
ProcessMap each event into a joinable envelope (our ingest.v1-class contract): stable fields such as ts (UTC), ci_id (or a key that will bind), signal, value, optional threshold / severity / modality tags. Drop or quarantine malformed rows
OutputNormalized stream — same meaning across sources so later stages can join by identity + time

Without Normalize, Fan-out and Detect see incompatible schemas; Localize cannot hang metrics/logs on one CI.

3. Topology bind (CI graph + identity)

Yes — this is the relationship / dependency graph Localize will walk (and that Tailor will slice). It is not a request trace.

PieceWhat it is
CI (node)Typed entity: service, pod, VM, host, datastore, switch port, …
EdgeTyped relationship: calls, hosted_on, runs_on, uses_datastore, uplink, …
Bind LUTMap messy labels (IP, hostname, K8s name) → stable ci_id used in Normalize
InputDiscovery / CMDB / service-map crawler cues (and optionally call-edge hints from APM); parallel to Collect, not “after all metrics arrive”
ProcessBuild/refresh the typed CI graph; publish bind table so Normalize can resolve ci_id; mark edges with direction useful for upstream/downstream walks
OutputSnapshot graph (topology.json / A-TOPO / Smartscape analogue) + bind LUT consumed by Normalize and later Tailor/Localize

Granularity reminder: coarse enough for stable ticket IDs; fine enough that the true fault CI is a node; refresh on deploy/discovery.

4. Fan-out — what it means

**Fan-out = write the same normalized stream to one or more sinks/profiles without forking Detect.**

It is not “split the RCA algorithm.” It is cost / consumer routing:

Profile (example)What gets writtenWhy
Cheap (L0)Lean-oriented incident bundles / metric slices needed for classic LocalizeLower store + query cost
Rich (F1)+ structural / speed-tier feeds (Fed Dragonfly tg:/pc:, KG slice, richer modalities)Enable Murphy/Nezha / class C–D depth when paid for
InputNormalized envelopes (+ topology available for bind)
ProcessVector (or Python stand-in) routes events to configured sinks — file, Dragonfly, structural store, Lean bundle writer. Same Detect watches the shared logical stream
OutputPopulated stores / bundles ready for Maintain and Detect; one Detect path remains shared for fair engine compare

5. Maintain — how it works

Maintain = keep the estate usable over time (lifecycle), continuous.

ConcernWhat happens
IdentityPrefer service/host keys over ephemeral pod names when pods churn
Topology freshnessRebuild/patch graph on discovery/deploy; stale edges → wrong walks
Retention tiersHot (recent incident windows) / warm / cold; drop or downsample what Tailor will never need
SamplingTraces/logs: keep decisive coverage under cost caps
Clock syncShared time base so “onset” across modalities is comparable
InputFan-out sinks + live topology updates
ProcessTTL, compaction, resample, re-index, re-crawl; ops policies — mostly automated
OutputHealthy hot/warm stores + fresh graph that Detect/Tailor can query

3.5 Common confusion to avoid

ConfusionCorrection

“Clock A = Event Graph, Clock B = Knowledge Graph”No — orthogonal axes. Both tiers are written on A and read on B. See §3.6.

3.6 Clocks vs Federated two-tier design

People often map Clock A/B onto Federated’s two graph tiers. The intuition is useful; the 1:1 equation is wrong.

Plain reading (team shareable)

Tier 1 / Tier 2 ≈ where data lives (Federated storage split: Event Graph vs Knowledge Graph), and therefore which hop reads which store. Storage-first axis.

Clock A / Clock B ≈ workflow / job cadence, not another storage layer:

  • Clock A — continuous platform work + case bridge: collect → normalize → topo → fan-out → maintain → Detect → Curate → Tailor
  • Clock B — per-incident RCA algorithms: Localize → Identify → Verify

Together, A then B (with Tailor as the bridge) is the end-to-end story. The clocks use the tiers; they aren’t the same kind of split.

Two axes
Tier axis

Dragonfly (T1) · Vortex/DashMap (T2) — storage / data plane

Bottom line: tiers = data-plane layout; clocks = when work runs and which RCA/preprocess jobs run on that data. Orthogonal, intersecting.

4.6 Design insights

  1. 1. Primary graph = CI / service relationships; hang modalities on entities.
  2. 2. Tailor like vendors: seed → neighborhood → corridor.
  3. 3. Copy evidence discipline, not causal marketing.
  4. 4. Compete where they stop: multimodal Identify + optional automated path Identify.
  5. 5. Cheap vs rich retention is normal — full dual-engine lake is expensive.

7. Scenario classes A–E (what “class C–D” means)

7.1 Purpose of the taxonomy

When someone says “we need logs for class C–D,” they mean:

This incident type usually cannot finish trustworthy Identify (and sometimes Localize) on alerts + metrics + topology alone — it needs richer modalities.

Classes are planning priors for data requirements and product claims. They are not:

  • ObserveOps UC-1..5 IDs
  • Severity levels (P1/P2)
  • Vendor feature names

“Reliably RCA’able” below ≈ useful Step-1 Localize with high confidence; Identify called out separately.

7.2 Class definitions (detailed)

9. Detect vs symptom seed

TermDefinition
DetectSomething is wrong → anomalies (thresholds / SLOs / Watchdog-class).
Symptom seedStart Localize at (CI, signal, time). Usually not the root.
Shared DetectWhen comparing engines: one Detect path so Localize comparisons stay fair.
Gray-failure DetectSoft unhealthiness without hard thresholds — optional upgrade; not required to define the jobs.

Production bar: stream → Detect → seed → Localize — not only pre-baked seeds in packs.
