1. Letters: pillar vs door vs Gate vs phase

Are A, B, and C doors, phases, or pillars?

Three lettered systems sit on the mapping pages. They do not line up 1:1. Bare “A”, “B”, or “C” means pillar unless the word door or Gate is in front.

Door A / B / C E6 Detect entry points A = Node trigger · B = Gateway trigger · C = platform monitor Not pillars. Door C reads Pillar A; it is not Pillar C.

“C is Clock B” was a bad sentence. It meant Pillar C runs in P3, not that C is a phase or a door.

Where do the pillars sit?

Pillar A and Pillar B are always-on P1 stores (write path). P2 and P3 only read them. Pillar C is optional P3 / Layer I. P2 has no Motadata pillar.

2. What the three pillars are

What are the three pillars in the Motadata PDF?

Products, not phases, not Detect doors.

Pillar A

Percentiles

Compact “is this weird?” store — T-Digest, buckets, seasonal baseline.

Pillar B

Knowledge graph

Typed “who is connected / what changed?” map. Smartscape-shaped job, not a service map.

Pillar C

Rust ReAct agent

Bounded diagnose/close. Our Layer I, opt-in. D5 stays Review.

The PDF is centralize-then-analyze (the SaaS column). It does not specify Node E1–E2, mask/Drain, Detect door A, or Gateway door B.

3. Pillar A pipeline (sketches)

What does Telemetry → windowing → seasonal baseline → T-Digest + bucket sketch → Vortex/S3 → O(1) index mean?

Only Pillar A’s write path. A sketch is a small stored summary of many samples — not a drawing, and not the raw time series. Goal: p95 / “normal for this slot” without replaying weeks of points.

TermMeaning

Consumers: dashboards, E6 door C, E10 get_metric_baseline(). Pillar A does not name the leaf (E9). Drain on the Node is a different “pattern” — volume reduce, not this store.

Motadata lists Container, Pod, Network, Change, Alert… Many have no persistent unique id. Wrong?

The CI bar is right: localize and ticket need a stable id (or a scoped id plus a validity window) on tenant+ci_id. Motadata used “entity” for any typed graph vertex, including events.

5. Motadata edges — four jobs

How do we segregate CALLS, DEPENDS_ON, RUNS_ON, CONTAINS, … RESOLVED_BY?

Four jobs. Only the first two belong on E3 GraphSnapshot.

1. Structure (CI–CI, often authoritative) — CONTAINS, RUNS_ON, DEPLOYED_AS only if you pick one meaning (k8s resource or release). Our analogues: part_of / runs_on / hosted_on.

2. Runtime / contract (CI–CI, service-map core) — CALLS, DEPENDS_ON, CONNECTS_TO, PRODUCES / CONSUMES. CALLS is the service map; DEPENDS_ON is wider.

3. Change hitch (CI–event) — CHANGED_BY, TRIGGERED, DEPLOYED_AS in the release sense. Change is a fact with a time, not a CMDB CI.

4. Case / close (not E3) — AFFECTS is blast radius at E9/E11. CORRELATED_WITH is E7 Curate (one CaseSeed, D3). RESOLVED_BY is E11 Package. Motadata folding Curate into Pillar B is exactly CORRELATED_WITH on the graph. We do not.

Can the same edges be bucketed upstream / downstream / peer?

Only buckets 1–2, and only relative to a seed. Upstream/downstream is a walk orientation, not a property of every Motadata edge type. RUNS_ON / CONTAINS are vertical. Peer is same-tier (clustered_with) — Motadata did not name it. Change/case edges are not upstream/downstream.

6. Alert on the graph vs E6 Signal

Motadata reifies Alert as a graph node, but alerts are E6 Signals?

Both. Two uses of “node”:

  • CI node — tenant+ci_id, leaf, maybe ticket. Alert is not this.
  • Fact / event vertex — Motadata draws Detect output on the map so it can store TRIGGERED / CORRELATED_WITH.

For us: Detect emits a Signal (E6). It points at a CI. It is not a vertex in GraphSnapshot. Curate merges signals (E7). Same split for Incident (CaseSeed) and Change (fact, not localize target).

Do Dynatrace / Datadog / Edge Delta have fact/event nodes on the map?

They have the objects. They do not treat them as topology vertices. Join is identity + time, not Alert as a neighbor of Service on the same graph.

7. Four designs, then merge 3 + 4

Is Motadata’s knowledge graph Smartscape or a service map?

Closer to Smartscape’s job than to a service map. It is neither product.

A service map is usually one layer: services + CALLS (Datadog APM, ED eBPF). Hop budget. No host→pod→process, no Change/Alert vertices.

Smartscape is Dynatrace’s typed multi-layer topology. Davis walks it, then pulls Grail on the same entityId. Map ∥ lake.

Motadata Pillar B aims at that RCA walk, then also hangs Change / Alert / Incident as vertices.

3rd design or 4th?

Should the final design be a hybrid of 3 and 4?

Yes — one graph, two planes. Column 3’s CI plane is canonical. Column 4’s extras are either folded into E3/E5 as time on CI edges, or kept off E3 as P2/P3 objects. Not “union every Motadata entity type.”

Node kinds

What
What is allowed to be a vertex. A CI node has tenant+ci_id; E9 may name it as a leaf and E11 may ticket it. A fact/event vertex is a time-stamped object (Alert, Incident, Change-as-entity) drawn as if it were a neighbor of a service.

Why
If Alert is a vertex, Curate and Detect leak into E3. You cannot tell “who exists in the estate” from “what fired this minute.” If only eternal CMDB CIs are vertices, a Pod that lived for ten minutes cannot appear on the walk at all.

Graph time

What
When a map fact was true: “this pod existed,” “this RUNS_ON held.” Motadata names it valid_from / valid_to. We already have per-edge refresh and E5 decay (declared 7d / 30d). This is not when the alert fired (E6) and not the E8 investigation corridor.

Why
Without it, a replaced pod or a stale declared cluster membership still looks live, and E9 walks a ghost. Topology history is P1 work. Detect must not be the first place time appears on the map.

Provenance

What
Why we believe this edge. Our three epistemic types: authoritative (owner system), declared (CMDB said so), corroborating (inferred from traces/flows). Plus confidence, discovered_via, refresh. Motadata stores confidence + source.

Why
Half a real graph is inference. If the operator cannot see that app → db came from a sampled trace, the verdict’s confidence is decoration. Ranking should degrade when the path walks declared or corroborating (specified; not lab-validated yet).

Structure + runtime edges

What
CI–CI relationship types. Structure = stack (CONTAINS, RUNS_ON, part_of). Runtime / contract = who talks to whom (CALLS, DEPENDS_ON, PRODUCES / CONSUMES). Our catalog has 15 names. Motadata’s CALLS list is the same two buckets plus case edges — those case edges are not this topic.

Why
E8 hop budget and E9 leaf search need typed walks (down the stack vs along callers). A service map is only the runtime bucket. RCA needs both.

Change

What
Something in the estate was modified — deploy, config, git SHA, change ticket. Motadata makes Change a vertex with CHANGED_BY. We reserved change_event as a signal_class and do not Collect it this pass.

Why
The walk “deps → recent changes → abnormal metrics” is how you stop blaming the symptom app for a bad release. That hitch is real. Making Change a CI (ticket root, eternal id) is not: a change is an operation with a time, not a host.

Alert / Incident

What
Detect output vs case object. Alert / Event / Signal = something looks wrong now (E6). Incident / Problem / CaseSeed = curated one-case (E7). Motadata draws both as vertices and links them with TRIGGERED / CORRELATED_WITH.

Why
DT/DD/ED keep these off Smartscape / Service Map and join by identity. If we copy Motadata, E3 becomes the case bus, D3 Curate disappears into an edge, and every storm pollutes the topology.

Impact / close

What
Impact (AFFECTS) = blast radius: who hurts if this leaf is down. Close (RESOLVED_BY) = ticket, verdict, or person that closed the case. Motadata stores both as graph edges. We compute impact at E9/E11 and emit close as VerdictCard / optional ITSM.

Why
Blast radius depends on the current walk and the current seed. Persisting AFFECTS as a standing topology edge goes stale the next deploy. RESOLVED_BY is a case outcome, not “who contains whom.”

Walker

What
Who reads the graph to name a leaf. Ours: E8 cuts hops/time, E9 applies a leaf rule; Layer I / ReAct is optional (D5 Review). Motadata: the Rust agent walks, with a written recipe (Incident → service → deps → changes → metrics).

Why
If the agent is the graph, the operator path dies and D5 flips. The recipe is still useful as E9 search order, not as a product that owns topology.

Store

What
Where the map and the evidence live. Dynatrace: Smartscape ∥ Grail. Ours: E3 ∥ E4 dests, same ci_id (D2). Motadata: Vortex/S3 holds graph and sketches (both rooms).

Why
One warehouse is simpler to demo and easier to lock in as “the” lake. We stay dest-agnostic (Gate B): Vortex may be one dest profile. Sketches are an E4 modality, not a second map. The agent must not scan the lake (that bound is E8).

Merged solution — one E3 GraphSnapshot

  1. Vertices = CIs (tenant+ci_id), including time-bounded runtime CIs (Pod/Container) with valid_from/valid_to (or equivalent) and a scope_parent. No Alert, Incident, ITSMTicket, Metric, Trace, LogPattern vertices.
  2. CI–CI edges = our 15 types + Motadata buckets 1–2, each with provenance and a validity window. Service-map CALLS is one family (communicates_with), not the whole graph.
  3. Change = optional fact records (not CIs) attached by CHANGED_BY, admitted later as change_event, not E1 this pass.
  4. Detect / Curate / Package stay E6 / E7 / E11. The Motadata walk is how E9 reads the CI graph + facts + E4, not extra vertex types.
  5. P2 still has no pillar. Retrieval bounds stay E8. Pillar C stays opt-in Layer I. Do not flip D5.

That is Smartscape’s job (columns 2/3) with Motadata’s temporal CI edges and change hitch, without Motadata’s event-node bus.

7b. Grail analogue

Pillar B ≈ Smartscape. Do we have anything parallel to Grail?

Yes: E4 Stores. We did not brand a first-party lake. Dynatrace’s split is Smartscape (map) ∥ Grail (evidence) on one entityId. Ours is E3 GraphSnapshot (map) ∥ E4 dest query surfaces (evidence) on one ci_id (D2 Signed). The map does not rebuild from the lake.

Motadata Vortex/S3 puts both rooms in one product: historical observability (sketches) and the knowledge graph. That is Grail plus Smartscape in one warehouse. We keep the rooms separate.

8. valid_from / valid_to — graph time, not Detect

Time bounds are not part of the knowledge graph; they appear at E6 Detect, right?

No. Motadata valid_from / valid_to are when a graph fact was true (edge/node history). That is E3 write + E5 Maintain. Our analogue: per-edge refresh, declared-edge decay (7d soft / 30d hard). We did not copy the Motadata field names; we copied the job.

E6 is a different clock: when the Signal fired. E8 locks the investigation corridor.

Do not merge these three. Graph time stays P1. Detect time stays P2.

9. Locked takeaways

  • Pillars ≠ doors ≠ Gates ≠ phases.
  • Door C consumes Pillar A; it is not Pillar C.
  • Alert = Signal (E6), not a CI. DT/DD/ED agree: events are off the topology map.
  • Canonical graph = SaaS E3; Gateway assist may look like a service map. Grail analogue = E4.
  • Hybrid 3+4 = temporal CI graph + Change-as-fact; not Motadata’s event vertices.
  • Do not flip D5. Operator E9–E11 must work with Pillar C off.

10. ToDo — leadership PDF vs our pipeline

What are we actually supposed to do with the Motadata PDF?

We already designed a pipeline called ObserveOps: eleven stages named E1 through E11 (Collect through Package). That design came from studying vendors (Dynatrace, Datadog, Edge Delta), not from this Motadata PDF.

Leadership then handed us a 4-page requirements sketch (Motadata Observability 3 Pillars Architecture). It describes three products (percentile store, knowledge graph, Rust ReAct agent) and a hosted stack that starts at a streaming bus called NATS.

ToDo is not “rebuild Motadata.” Put each PDF box next to the matching ObserveOps stage. Where they fight, write a resolution that does not throw away the eleven-stage clock. Compact twin: job map.

Terms this section uses

Node — software on the customer machine (or sidecar) that first sees telemetry. SaaS — our (or Motadata’s) hosted side. Shift-left means: do as much Collect / Identity / optional Detect as we can on the Node (or an optional Gateway) before data is sent over TLS to SaaS. The Motadata PDF only draws the SaaS side.

E1 Collect — admit raw telemetry. E2 Identity — attach a stable id: tenant (which customer) + ci_id (which configuration item, e.g. the checkout service). The on-the-wire record shape is ingest.v1.

E3 — the topology map (GraphSnapshot). E4 — evidence stores (metrics/logs/traces, and compact percentile “sketches”). E6 Detect can fire in three places we call doors: A on the Node, B on a Gateway, C on the platform. E7 Curate merges many alerts into one case (CaseSeed). E8 bounds what we may query. E9–E11 localize, identify, and package a VerdictCard.

NATS — in the PDF, a message bus: collectors publish telemetry, SaaS engines subscribe. It is a pipe, not identity and not Detect.

Block-2 — the August–November 2026-27 OKRs in the KR Plan spreadsheet. Objective 1 is “Shift-left Node fabric” (ship Collect + Identity on the Node).

D5 — our HLD decision on whether an LLM/agent is the default way to package a case. It stays Review: the operator path (no agent) must always work. Do not flip D5.

Hybrid 3+4 is not a new product name. It is the bundle of resolutions for conflicts 2–5: keep our CI-only map; take Motadata’s time on map edges and sketches-in-the-store; refuse Alert-as-a-map-node and “the agent is Curate and Package.”

The PDF does not mention Node Collect, mask/redact, Drain (log-pattern reduce), Detect on the Node, or an optional Gateway. That omission is why conflict 1 exists — not because the PDF forbids those steps.

Already maps (not a fight). Their percentile sketches are the same job as our E4 compact history (Pillar A). Their “walk the graph to find where the fault sits” is the same job as E3 + E9. Their “don’t dump the whole lake into the agent” is E8. Their “evidence, not LLM assertion” is E10. Their explain/ticket is E11 (we call the artifact a VerdictCard). Restarting machines is not Package in our HLD.

Sketches ≠ map. Sketches = compact percentile history (Grail-like, E4). Map = who-is-connected graph (Smartscape-like, E3). Motadata Vortex+S3 draws both rooms in one product.

Longer explanation of each row follows.

Conflict 1 — Where does processing start?

PDF
Page 1, §1 Executive Architecture. They never say “central bus.” They draw Telemetry → Streaming Layer — NATS → Percentile Engine | Graph Builder → Vortex. Windowing sits after NATS. Collectors are unnamed.

Conflict
The PDF does not claim that intelligence starts only after NATS. Page 1 names engines after a streaming layer; it does not describe what collectors do before publish, and it does not forbid redact or identity on the Node. The mapping gap is: we must still write those Node steps; they are simply not in the picture.

Example
A pod log line contains a bearer token. The PDF does not say “send the token through NATS.” It also does not say “redact on the Node.” We still redact and stamp ci_id=checkout-api on the Node; NATS (if any) may carry the cleaned ingest.v1 record.

Resolution. We do not delay redact, Drain, or identity until after a central bus just because those boxes are missing from page 1. We keep shift-left: the Node still redacts secrets and stamps tenant + ci_id before data leaves the machine. The Motadata drawing is a SaaS-side stack (percentile engine, graph builder, Vortex, agent). It is not a statement that the Node is empty. If we use NATS at all, it is a message hop: records already went through Collect (and Identity where we bind). NATS does not replace E1 or E2. A NATS process on the Node is allowed as a local buffer. So E1 then E2 stay our work — the PDF is silent, not opposed.

Still ToDo (Block-2, objective 1 — Shift-left Node fabric): in the lab, show a Kubernetes and a VM stream leaving the Node as ingest.v1 with tenant and ci_id filled in, and with secrets not in the egress. That proves the PDF stack can sit on top of our edge, rather than instead of it.

They put sketches and the map in one product. We keep the map (E3) separate from evidence stores (E4). The map is not rebuilt by querying the lake at RCA time.

Example
“Give me p95 for checkout-api this Monday 9am” is an E4 sketch lookup. “Who does checkout call?” is an E3 edge walk. Same ci_id. You do not invent callers by scanning Vortex at query time.

Resolution. Do not put the map tables and the metric/log history in one mandatory warehouse named Vortex. Keep two rooms that share the same id (tenant + ci_id): E3 is who exists and how CIs connect; E4 is time-series evidence, including Motadata’s compact percentile sketches as one extra kind of history, not a second map. Vortex + S3 may be one tenant destination we can write to (Gate B: which storage product is this tenant’s dest). It is not required to be the only dest.

Still ToDo (production depth): finish LLD-E4 (Stores is still Draft); prove Gate B dests beyond files.v1 (Vortex and/or S3) on a Motadata-shaped path.
Lab / PoC (done for Block-2 sketch path): Pillar A sketch writer under pillar-ab-implementation/pillar-a/poc/ lands sketches in history/ via Gate B files.v1 (a non-Vortex dest). That does not close production Vortex+S3 temperature jobs.

Conflict 3 — Is an Alert a node on the map?

PDF
Page 2 core entities list Change, Alert, Incident, ITSMTicket next to Service and Host. Edges include TRIGGERED, CORRELATED_WITH, RESOLVED_BY.

Conflict
They draw Detect/case objects as graph neighbors of CIs. Our map is CIs only. Alert is an E6 Signal that points at a CI.

Example
Checkout p95 crosses a threshold. PDF: new vertex Alert-8831 with TRIGGERED → Service checkout. Us: Signal {ci_id: checkout-api, class: SLOWDOWN}. The graph still has checkout → payments. The alert is not a third node you hop through.

Resolution. The map stays CIs only (services, hosts, pods with a parent and a time window). An Alert stays an E6 Detect output (Signal) that names a ci_id. We do take one Motadata idea: when a map fact was true (valid_from / valid_to on CI nodes and CI–CI edges), written by E3 and refreshed by E5 — that is not “when the alert fired” (E6). A Change (deploy, config, ticket) is a timed fact we may attach later. It is not a configuration item we localize or ticket, and we do not ingest change tickets as Collect this pass.

Still ToDo (Block-2, objective 2 — P1 stores): ship a GraphSnapshot that has validity + provenance on CI edges, and that does not contain Alert/Incident vertices.

Conflict 4 — Who merges a storm into one case?

PDF
Page 2 edge CORRELATED_WITH. Page 3 tool deduplicate_incident() on the Rust agent.

Conflict
They fold Curate into Pillar C (the agent). We require E7 one CaseSeed before diagnose. The agent must not be the first place five alerts become one incident.

Example
Host CPU high, checkout 5xx, and payments timeout fire in one minute. PDF agent dedupes while walking. Us: E7 already emitted one CaseSeed; E8 then cuts hops/time; E9 walks that seed.

Resolution. Merging a storm stays E7 Curate, a required stage before any diagnose walk and before any optional agent (HLD D3: one seed per case). Motadata’s CORRELATED_WITH is the sentence we store on the case (“these three signals are the same incident because…”), not a permanent edge on the topology map.

Still ToDo (Block-2, objective 3 — case open without an LLM): emit one CaseSeed per correlated storm, with that merge rationale written down.

Conflict 5 — Is ReAct the RCA engine?

PDF
Page 1 ends at Rust RCA Agent. Page 3 state machine Observe → Retrieve → Decide, plus execute_remediation().

Conflict
The PDF’s default closer is the agent. Ours is deterministic E9–E11. D5 stays Review. The operator path must work with the Motadata agent (Pillar C) off.

Example
Same checkout 5xx. PDF: ReAct loops query_graph / get_metric_baseline until it names a leaf. Us: E9 applies a leaf rule using their walk order (service → deps → metrics); E10 pulls sketches; E11 writes a VerdictCard. No LLM required.

Resolution. Copy Motadata’s search order as how E9 Localize walks our CI graph plus E4 evidence. Do not make the Rust ReAct agent the default engine that performs that walk. D5 stays Review: an optional agent (Layer I) may be added later behind Gate D (on/off). Until then, and even after, E9–E11 must produce a VerdictCard with the agent off. Auto-remediation is outside this eleven-stage clock.

Still ToDo (Block-2, objective 4 — deterministic RCA close): close three Detect classes on the operator path, Layer I off. Do not schedule the ReAct agent in this block.

Conflict 6 — Where does Detect run?

PDF
Page 1 Pillar A: thresholds / anomaly boundaries; consumers include alerts. All of that sits after Vortex. No Node trigger.

Conflict
That is only door C (a platform monitor on sketches). We also have door A (Node) and door B (Gateway). Door C reads Pillar A sketches; it is not Motadata Pillar C (the agent).

Example
Disk full on a VM can fire on the Node in seconds (door A). “p95 for this weekday-hour is weird” needs sketches, so it waits for door C. Both are Detect. The PDF only drew the second.

Resolution. Build the PDF’s sketch-based alerting as door C. Separately keep door A (Node can fire when the machine already knows) and door B (optional Gateway). Write Gate C: which Detect classes are allowed only on the platform.

Still ToDo: write the Gate C decision; show door C firing on at least two Detect classes (for example ERROR and SLOWDOWN).

Conflict 7 — Are tickets and remediations ingest?

PDF
Page 1 Telemetry line includes ITSM; stack ends Explain / ITSM / Remediate. Page 3 tools create_ticket() and execute_remediation().

Conflict
They list ITSM with Collect, and remediation in the same loop as Package. We Collect telemetry only. Ticket is an E11 output. Restarting a pod is not one of E1–E11.

Example
A ServiceNow change ticket is not an ingest.v1 log line. We may emit a ticket when packaging a verdict. We do not restart a pod from E11 this pass.

Resolution. E1 Collect this pass is logs/metrics/traces/events from the estate — not ServiceNow tickets. Creating a ticket is an E11 Package output (optional). Executing a fix is out of this pipeline.

Still ToDo: keep that boundary in Block-2 (objective 4 lists ReAct, remediation, and ITSM-as-Collect as out of scope).

Conflict 8 — Who creates entity_id?

PDF
Page 1 sketch field entity_id; page 2 graph entity_id / entity_type / tenant_id. No bind overlay, no “unresolved” state.

Conflict
Not a fight — a gap. They assume every row already has a stable id. We have E2 Identity: if we cannot bind, we do not ticket that id (D-E2-1).

Example
A log with only pod_name=web-7f2 and no service. PDF sketch row still wants entity_id. Us: bind to ci_id when we can; if we cannot, do not localize or ticket that id.

Resolution. E2 Identity runs before any sketch row or graph node is written. If we cannot bind a stable ci_id, we do not treat that id as a localize target or a ticket root. Motadata’s entity_id is the same kind of key once bound; they just skipped drawing the bind step.

Still ToDo: same as conflict 1 — prove ingest.v1 already carries tenant + ci_id on the Node. That is the precondition for Pillars A and B.

Open until Block-2 work finishes: D5 and Gate D stay Review (the optional agent stays off by default). The written specs for Topology (LLD-E3) and Stores (LLD-E4) stay Draft until those stores actually exist in the lab.
