Two fan-outs (do not confuse)

1 · Stream fan-out (after E2)

Identity has already stamped tenant + ci_id and identity.status (look-up / bind done). The identified stream splits to E3 Topology (Pillar B → map/) and E4 sketch writer (Pillar A → history/) in parallel.

2 · Destination fan-out (lake product)

Writers call Dest.put(room, …). The dest profile chooses the physical product: Vortex+S3, lab files, Motadata store, or another lake. This is not the same fork as map vs history.

Two axes inside the Motadata-shaped dest

Rooms (content)

map/ = knowledge graph (graph_node.v1 / graph_edge.v1 / GraphSnapshot). history/ = sketches (sketch.v1). Same configuration items; different facts. Join by identity — not by temperature.

Vortex + S3 (temperature)

When this dest is chosen: two complementary tiers — not two copies of the same architecture with different TTL. Vortex = hot query engine; S3 = cold durable store. Both hold the same kinds of rows as colder or hotter encodings. Both rooms can live hot and spill cold. Lab may use only files.

Same logical records · different architecture

A common question: are Vortex and S3 “the same structure” except for hot vs cold? Similar in data model; not similar in architecture. They share the ObserveOps logical contract — same row kinds (graph_node.v1, graph_edge.v1, sketch.v1), join keys (tenant + ci_id / entity_id), and rooms (map/, history/) — but they play different jobs in the Motadata-shaped destination. Hot/cold names the temperature split; the important distinction is query engine vs object store.

One line

S3 = remember. Durable, append-only history. Vortex = query fast. Interactive analytical engine plus the only diagnose-facing query surface for this dest. Diagnose builds a bounded WorkingSet through the Vortex query layer — never by opening S3 directly.

Full interaction diagram

Who “agent” is (and is not)

Motadata Pillar C · Rust ReAct agent

In Motadata materials, agent means the optional diagnose loop (Layer I / Interpret): observe case → tools against a bounded evidence set → propose. It is not Collect, Topology, E4 writers, or “any HTTP caller.” On our pipeline the same rule is broader: the whole diagnose path (retrieval, Localize, Identify, and optional ReAct) must not open S3 or hop-scan Vortex as a dump. Operator E9–E11 must work with ReAct off.

Retrieval ──► WorkingSet ──► Localize / Identify └──► optional Rust ReAct (tools only inside that budget)

Three interaction patterns

Use the tabs below for full-width animated views of how Vortex (hot) and S3 (cold) interact after writers land rows in map/ and history/. Retrieval (E8 Scope) queries through the Vortex query layer — never S3 directly. RCA phases start at E9 Localize (E6 is Detect, upstream). Deep links: pattern 1 · pattern 2 · pattern 3.

1 · Hot write → Vortex; cold spill → S3

Fresh rows from both writers land in Vortex first (map/ and history/). As windows age past a retention threshold, Vortex spills those rows to S3. Hot working set stays small; S3 holds history cheaply.

Pillar A∥B writers ──► Dest ──► Vortex (hot) ──age-out──► S3 (cold)

2 · Federated read-back: Vortex query layer pulls from S3 on demand

When Retrieval (E8 Scope — building a case WorkingSet) asks for data older than the hot window, the Vortex query layer scans relevant S3 partitions and merges them into the response. E9 Localize and E10 Identify consume that set; they never talk to S3 directly. E6 Detect (door C) is upstream — it reads hot sketches to fire signals, not this federated read-back path.

Retrieval ──query──► Vortex query layer ──scan──► S3 ──merge──► WorkingSet

3 · Immutable archive: S3 is the cold system of record

Once a GraphSnapshot version or sketch batch is on S3, it is immutable. Topology change → new snapshot version. Sketch correction → new row with later write time. S3 is durable history; Vortex is the fast query cache on top.

S3 = durable append-only · Vortex = hot cache · never mutate cold rows

What each component is not

Vortex is not

Not the pipeline (Collect / Identity / writers write into it). Not the only E4 dest forever. Not the ReAct agent — Retrieval uses the query layer; the optional agent only sees a WorkingSet.

S3 is not

Not a query engine. Not opened by Retrieval, Localize, or the Rust ReAct agent. Not mandatory in lab (file dest is fine). Not a second schema — colder copies of the same rooms.

Neither fan-out is Vortex

Stream fan-out = after Identity (map vs history writers). Destination fan-out = which product receives rows. Vortex/S3 answers only the second question.

Key rule: Identity bind first → stream fan-out into map/ ∥ history/ → dest profile (Vortex+S3 or files) → Vortex query layer → WorkingSet. Rooms = content. Vortex / S3 = temperature and role (query engine vs object store) — same logical records, different architecture. Same schema · different role · Parquet vs Lance encodings.
