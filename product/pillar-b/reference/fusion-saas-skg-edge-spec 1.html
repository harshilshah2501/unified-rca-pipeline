The Fusion SaaS SKG edge specification.

Fifteen relationship types — eleven stored as ground truth, four computed at query time — designed to answer the four operational questions of a modern CMDB: blast radius, incident routing, change risk, and cost attribution. This document is the single technical spec all engineering work references.

§ 01 · Why these fifteen

A small, opinionated vocabulary — verified against twenty years of enterprise CMDB practice.

Every edge type in this spec was selected because it satisfies five criteria simultaneously. Edge types that satisfy fewer than all five did not ship. This section explains the gate.

Criterion 01

One-sentence operational meaning

Every edge type can be defined in a single sentence describing what it asserts about the real world. If the meaning needs a paragraph, the edge is doing too much.

Criterion 02

Cross-platform precedent

Every edge has a direct conceptual analogue in at least two of the major enterprise CMDB models. None is invented from scratch — all are battle-tested concepts under cleaner names.

Criterion 03

Distinct lifecycle behavior

Every edge has a defined answer to "what happens to the target when the source is deleted" — cascade, detach, or independent. No ambiguous behavior at delete time.

Criterion 04

Serves at least one core use case

Every edge contributes to one or more of: blast-radius computation, incident routing, change risk, cost attribution. Edges that serve none are documentation noise.

Criterion 05

Discoverable or governance-derived

Every edge has a realistic evidence source — a discovery probe, agent telemetry, IaC parse, API integration, or human-authored governance record. Edges that nothing can produce are useless.

The design philosophy

Store the facts that the world can produce. Compute the truths the operators need. Eleven stored edges hold ground truth; four computed edges derive blast radius, reachability, failure domain, and criticality without ever being written to the graph.

These principles govern every choice in this document. If a future change would violate one of them, it requires explicit override in the decision log.

§ 04 · The eleven stored edges

Ground truth — what the world can produce.

These are the only edges written to the graph. Discovery probes, agents, IaC parsers, API integrations, and human governance flows all produce one or more of these. Anything outside this list is rejected at the API boundary.

Edge 01 · Composition

composedOf

A composedOf B  /  B partOf A
cascade delete identity impact 1:N
B is a structural part of A; B has no meaningful existence outside A and is destroyed when A is destroyed.
Lifecycle
Cascading delete. When the source is removed, the target is removed automatically. No orphans.
Direction
Directional. Source is the whole; target is the part.
Cardinality
One source has many parts (1:N). Each part has exactly one composing parent.
Identity-contributing
Yes. The part's identity is "the part inside this specific whole."
Impact-bearing
Yes. Failure of the whole implies failure of the part; failure of the part may degrade the whole depending on redundancy.
Worked examples Server composedOf CPU, Disk, Memory, NIC VM composedOf Process, FileSystem (per-VM) vCenter composedOf Inventory Database, SSO Domain, Certificate Authority Kubernetes Pod composedOf Container, Init Container, Volume Mount
Valid source → target classes
  • PhysicalServer → CPU, Disk, Memory, NIC, PowerSupply
  • VirtualMachine → Process, FileSystem (VM-local), VirtualDisk
  • NetworkDevice → Interface, Port, LineCard
  • Container → Process, MountedVolume
  • SoftwareInstance → InternalModule, EmbeddedDatabase, EmbeddedService
Typical evidence sources
  • Agent telemetry (highest confidence — 0.95+)
  • Discovery probe with credentials (SNMP, WMI, SSH, API)
  • API integration with hypervisor or cluster control plane
  • IaC parsing (Terraform, CloudFormation, Helm — for declared composition)
Anti-pattern Do not use composedOf for relationships that survive parent deletion. A datacenter is not composedOf servers — servers can be relocated. Use contains instead. The cascading-delete behavior of composedOf is non-negotiable; if you don't want cascade, you don't want this edge.
Edge 02 · Logical containment

contains

A contains B  /  B containedIn A
detach on delete no identity cond. impact 1:N
A logically holds B at this moment in time, but B is an independent entity that survives A's deletion or relocation.
Lifecycle
Detach on delete. When A is removed, the edge dissolves but B persists as an unattached record.
Direction
Directional. Source is the container; target is the contained entity.
Cardinality
1:N typical. A contained entity belongs to one container at a time but may move.
Identity-contributing
No. B's identity is independent of A.
Impact-bearing
Conditional. Depends on what the containment represents operationally.
Worked examples Node contains IPAddress (IP can be reassigned) DatabaseInstance contains Schema (schema can be exported and moved) Datacenter contains Rack, Server (assets can be relocated) vCenter Datacenter contains Cluster, Distributed Switch, Datastore
Valid source → target classes
  • Node → IPAddress, Hostname
  • Datacenter / Region → Rack, AvailabilityZone, NetworkSegment
  • DatabaseInstance → Schema, Tablespace
  • NamespacedScope (K8s Namespace) → Pod, Service, ConfigMap, Secret
Typical evidence sources
  • API integration (cloud provider, vCenter, K8s API)
  • IaC parsing
  • Manual placement records
Anti-pattern Do not use contains for lifecycle-bound parts. A server's CPU is not contained by the server — it is composedOf the server. The CPU has no business existing outside the server record.
Edge 03 · Runtime hosting

runsOn

A runsOn B  /  B runs A
detach on host delete identity impact N:1
A is a runtime instance whose execution is hosted by B's runtime substrate; A's identity is partly defined by where it runs.
Lifecycle
Detach when host is deleted; the runtime instance becomes orphaned but the source record may persist for genealogy. Restart on a new host creates a new runsOn edge.
Direction
Directional. Source is the running entity; target is the host.
Cardinality
N:1 typical. Many runtime instances on one host; each instance on exactly one host at a time.
Identity-contributing
Yes. "Tomcat 9 on linux-prod-42" is identified differently from "Tomcat 9 on linux-stage-07." This is the canonical use of identity-contributing edges for reconciliation.
Impact-bearing
Yes. Host failure implies hosted-entity failure.
Worked examples Process runsOn OperatingSystem OperatingSystem runsOn VirtualMachine VirtualMachine runsOn Hypervisor Application runsOn ApplicationServer Container runsOn KubernetesNode DatabaseInstance runsOn OperatingSystem
Valid source → target classes (selected)
  • Process → OperatingSystem
  • OperatingSystem → VirtualMachine, PhysicalServer
  • VirtualMachine → Hypervisor
  • Container → ContainerHost, KubernetesNode
  • Pod → KubernetesNode
  • Application, DatabaseInstance, MessageBroker → OperatingSystem, ApplicationServer
Typical evidence sources
  • Agent telemetry on the host (highest confidence)
  • Discovery probe with credentials
  • Hypervisor / control-plane API (vCenter, K8s, cloud provider)
Anti-pattern Do not chain runsOn more than logically necessary. Process → OS → VM → Hypervisor is a four-hop chain that the impact computation handles correctly. Do not collapse it into "Process runsOn Hypervisor" — that loses the OS and VM as reconciliation anchors.
Edge 04 · Operational dependency

dependsOn

A dependsOn B  /  B usedBy A
independent lifecycle no identity impact N:M
A requires B's function to operate correctly; if B is degraded or unavailable, A is degraded or unavailable.
Lifecycle
Fully independent. Neither side cascades to the other on delete. The edge may be marked stale if either side disappears.
Direction
Directional, matching English. Source is the dependent; target is the provider.
Cardinality
N:M. A service can depend on many things; one provider can be depended on by many.
Identity-contributing
No. The dependent entity exists independently.
Impact-bearing
Yes. This is the canonical edge for blast-radius computation across hosting boundaries.
Worked examples Application dependsOn DatabaseInstance BusinessService dependsOn ApplicationService Application dependsOn IdentityProvider vCenter dependsOn ActiveDirectoryDomain, DNSServer, NTPServer, vCenterDatabase PaymentService dependsOn FraudCheckService, LedgerDatabase, MessageBroker
Valid source → target classes
  • Any Application, Service, BusinessService, ApplicationService → any DatabaseInstance, MessageBroker, IdentityProvider, ApplicationService, ExternalAPI
  • Management software (vCenter, K8s control plane, Domain Controller) → any backing data store, identity source, time source, name resolution source
Typical evidence sources
  • Service mapping session (human-authored)
  • Traffic observation (NetFlow, eBPF, packet capture) — yields a candidate dependency that may need confirmation
  • Log inference (AI-derived from request logs)
  • Configuration parsing (connection strings, service references in manifests)
Anti-pattern · most common in practice Do not model "A talks to B" as dependsOn automatically. A service calling B with idempotent retries and a circuit breaker does not depend on B in the operational sense. Use communicatesWith for the traffic; promote to dependsOn only when the operational claim has been validated (typically by service mapping or runtime SLO behavior).
Edge 05 · Observed communication

communicatesWith

A communicatesWith B  /  (symmetric)
independent lifecycle no identity cond. impact N:M
A and B have been observed exchanging data over the network; this is empirical evidence, not an operational claim.
Lifecycle
Independent. Edge is refreshed by ongoing observation; goes stale and is removed if not re-observed within its TTL.
Direction
Typically bidirectional. May carry a "primary direction" attribute when the traffic is asymmetric (e.g., client → server).
Cardinality
N:M.
Identity-contributing
No.
Impact-bearing
Conditional. Only included in blast-radius computation when promoted to dependsOn by validation, or when explicitly requested by the query.
Worked examples WebFrontend communicatesWith AuthService (port 443, ~200 req/s) DatabaseInstance communicatesWith ReplicaDatabaseInstance (port 5432, replication traffic) vCenter communicatesWith ESXHost (ports 443, 902) Server communicatesWith NetworkDevice (LLDP / CDP discovery)
Edge attributes specific to this type
  • protocol · TCP, UDP, HTTPS, gRPC, AMQP, etc.
  • port · destination port
  • volume · packets/sec or bytes/sec, time-windowed
  • direction · symmetric, source-to-target, or target-to-source dominant
Typical evidence sources
  • Traffic observation (NetFlow, sFlow, eBPF, packet capture)
  • Agent telemetry (per-process socket inventory)
  • Service mesh telemetry (Istio, Linkerd)
  • Layer 2 / 3 discovery (LLDP, CDP, SNMP)
Anti-pattern Do not silently use communicatesWith in blast-radius queries by default. Observing traffic does not establish operational dependency. The graph engine must keep these two concepts distinct or impact computation produces false positives.
Edge 06 · Service realization

realizes

A realizes B  /  B realizedBy A
independent lifecycle no identity impact N:M
A is a concrete entity that fulfills an abstract concept B; without A (or alternative realizers), B has no operational substance.
Lifecycle
Independent. A realizer can be replaced without destroying the realized concept.
Direction
Directional. Source is the concrete realizer; target is the abstract concept.
Cardinality
N:M. Multiple realizers per concept; one realizer may serve multiple concepts.
Identity-contributing
No.
Impact-bearing
Yes. When all realizers of a business concept are degraded, the concept itself is degraded.
Worked examples ApplicationService realizes BusinessCapability ServiceOffering realizes BusinessService RunningSoftware realizes SoftwareProduct PaymentMicroservice realizes BusinessCapability "Accept Payment"
The default service realization spine

Fusion SaaS ships an opinionated default chain that customers customize from:

BusinessCapability ← realizes ← BusinessApplication BusinessApplication ← realizes ← ApplicationService ApplicationService ← realizes ← TechnicalService / RunningSoftware
Typical evidence sources
  • Service mapping session (human-authored, primary)
  • Manual governance records
  • AI-inferred from naming conventions, repo tags, organizational data
Anti-pattern Do not confuse realizes with composedOf. A business capability is not composed of microservices — it is realized by them. The microservices can be swapped without changing the capability's identity. composedOf implies cascade-delete; realizes does not.
Edge 07 · Logical grouping

memberOf

A memberOf B  /  B hasMember A
detach on delete no identity cond. impact N:M
A belongs to a logical collection B; the collection groups its members but does not own or contain them in a structural sense.
Lifecycle
Detach on collection delete. Members survive.
Direction
Directional. Source is the member; target is the collection.
Cardinality
N:M. A member can belong to many collections.
Identity-contributing
No.
Impact-bearing
Conditional. Cluster membership is impact-bearing (cluster outage affects members); tag-based grouping typically is not.
Worked examples Node memberOf KubernetesCluster Server memberOf HAFailoverGroup Server memberOf LoadBalancerPool IPAddress memberOf Subnet VM memberOf ResourcePool
Typical evidence sources
  • API integration (cluster controllers, load balancers, cloud resource groups)
  • Configuration parsing
  • Manual tagging
Anti-pattern Do not use memberOf for hosting relationships. A pod is not a memberOf its node — it runsOn the node. Membership implies grouping equivalence among peers; hosting implies hierarchical substrate.
Edge 08 · Control-plane management

manages

A manages B  /  B managedBy A
independent lifecycle no identity cond. impact N:M
A is the management plane that controls, configures, or orchestrates B's lifecycle and configuration; B can continue functioning if A is unavailable but cannot be reconfigured.
Lifecycle
Independent. The managed entity is operationally autonomous.
Direction
Directional. Source is the manager; target is the managed.
Cardinality
N:M typically. One manager covers many managed entities; an entity may have backup managers.
Identity-contributing
No.
Impact-bearing
Conditional. Manager outage affects the ability to change the managed entity, not its current operation. Excluded from default blast-radius unless explicitly requested.
Worked examples vCenter manages ESXHost, VirtualMachine, vSphereCluster, DistributedSwitch, Datastore KubernetesControlPlane manages KubernetesNode, Pod, Deployment ConfigurationServer manages Server (target of Ansible / Puppet / SCCM) DomainController manages DomainJoinedHost
Typical evidence sources
  • API integration with the management plane (vCenter API, K8s API, AD)
  • Configuration management system telemetry
Anti-pattern · the vCenter mistake Do not model "VM dependsOn vCenter." Discovery tools commonly emit this and it produces false blast-radius results — a vCenter outage falsely appears to take down every VM in the estate, when in reality the VMs continue running. Use manages for control-plane relationships and reserve dependsOn for operational dependencies.
Edge 09 · Governance accountability

ownedBy

A ownedBy B  /  B owns A
independent lifecycle no identity no impact N:1
A is accountable to B for the CI's existence, cost, compliance, and lifecycle decisions; B is a person, group, or organizational unit.
Lifecycle
Independent. Ownership transfers do not destroy the CI.
Direction
Directional. Source is the CI; target is the accountable party.
Cardinality
N:1. A CI has exactly one owner at a time (organizationally); the owner may have many CIs.
Identity-contributing
No.
Impact-bearing
No. Ownership is governance, not operations. Excluded from blast-radius.
Worked examples Application ownedBy User (Application Owner) BusinessApplication ownedBy BusinessUnit Database ownedBy CostCenter vCenter ownedBy InfrastructureLeadership
Typical evidence sources
  • HR or directory integration
  • Manual governance records
  • Tag-based attribution from cloud accounts
Anti-pattern Do not use ownedBy for operational responsibility. Ownership is "who answers to the auditor"; operational responsibility is "who gets paged at 3 AM." For operational responsibility, ownership of an OnCallRotation or SupportGroup CI is typically modeled via managedBy at the human-group level (a future extension; treat as v0.2 candidate).
Edge 10 · Placement

locatedIn

A locatedIn B  /  B houses A
independent lifecycle no identity cond. impact N:1
A is physically or logically placed within B; B defines a failure domain for events that affect physical or logical location.
Lifecycle
Independent. Location can change (relocation, migration).
Direction
Directional. Source is the placed entity; target is the location.
Cardinality
N:1. An entity is in one location at a time.
Identity-contributing
No.
Impact-bearing
Conditional. Used by sharesFailureDomain computed edge for location-correlated outages (datacenter, AZ, region).
Worked examples Rack locatedIn Datacenter VirtualMachine locatedIn AvailabilityZone Service locatedIn CloudRegion Datacenter locatedIn GeographicRegion
Typical evidence sources
  • Cloud provider API (region, AZ assignment)
  • Datacenter inventory system
  • Manual placement records
Anti-pattern Do not model logical groupings (a security zone, an application tier) as locatedIn. Use memberOf for logical groupings; locatedIn is reserved for physical or platform-defined locations that constitute genuine failure domains.
Edge 11 · Genealogy

succeedsLifecycleOf

A succeedsLifecycleOf B  /  B succeededBy A
independent lifecycle no identity no impact N:1
A is the successor of B in a deliberate lifecycle progression — version upgrade, replacement, migration, or sunset; both records persist for genealogy.
Lifecycle
Independent.
Direction
Directional. Source is the successor; target is the predecessor.
Cardinality
N:1 typical. A successor has one direct predecessor; many predecessors may collapse into one successor (merges).
Identity-contributing
No.
Impact-bearing
No. Genealogy is historical, not operational.
Worked examples Application v2.0 succeedsLifecycleOf Application v1.5 Server (new) succeedsLifecycleOf Server (decommissioned) CloudService succeedsLifecycleOf OnPremEquivalent
Typical evidence sources
  • Change records (manual or RFC-derived)
  • IaC parsing (Terraform state transitions)
  • Build pipeline metadata
Anti-pattern Do not model upgrades-in-place using succeedsLifecycleOf if no new CI was created. A patch to Server-01 is not a successor relationship — it is a CI attribute change. Reserve genealogy for deliberate replacements where both old and new CIs exist as records.
§ 05 · The four computed edges

Derived at query time — the operational truths.

These edges are never written to the graph. They are graph-traversal patterns that resolve at query time over the stored edges. This separates ground truth (what is) from operational truth (what it means), and lets the operational rules evolve without rewriting data.

Architectural commitment

The four computed edges below are the v0.1 set. Additional computed edges (security blast radius, compliance scope, change risk score) are anticipated as v0.2 candidates — they will be defined as new traversal patterns over the same eleven stored edges, never as new stored types.

Computed Edge 01

impactedBy

A impactedBy B  /  B impacts A
computed N:M
A is impacted by B if there exists a directed path from A to B through impact-bearing edges (runsOn, dependsOn, composedOf, realizes) where each hop preserves the operational claim "if downstream fails, upstream is affected."
Traversal definition

Starting from A, follow any sequence of impact-bearing stored edges in the dependent → provider direction. B is reachable in the traversal ⇒ B impacts A.

Edges included by default
  • dependsOn · always
  • runsOn · always
  • composedOf · always (cascade implies impact)
  • realizes · when traversing concrete → abstract
Edges excluded by default
  • communicatesWith · excluded — communication is evidence, not claim
  • manages · excluded — control-plane outage does not down workloads
  • ownedBy, locatedIn, memberOf, contains, succeedsLifecycleOf · excluded by default; can be requested explicitly
Use cases
  • Blast radius: "if this CI fails, what else is affected?" — query impactedBy in the reverse direction
  • Change risk: "what business outcomes are at risk if I take this CI down for maintenance?"
  • Root cause: starting from a failing service, find the smallest set of upstream failures that could explain it
Configurability

Customers can define alternate impact models by overriding which edge types contribute. E.g., a security-focused customer can include communicatesWith for lateral-movement blast radius. The default model is documented; alternates live alongside.

Computed Edge 02

reaches

A reaches B  /  B reachableFrom A
computed N:M
A can reach B if there exists any path from A to B through communicatesWith and dependsOn edges — irrespective of impact propagation. This answers reachability, not dependency.
Traversal definition

Transitive closure over the union of communicatesWith and dependsOn. Direction-aware: respects the directional attribute of communicatesWith when present.

Use cases
  • Security: lateral-movement analysis — "can a compromise of host X reach service Y?"
  • Network design: confirming connectivity for a planned integration
  • Compliance scope: which systems touch a regulated data store
Distinction from impactedBy

A can reach B without being impacted by B (idempotent retries, async messaging). Reachability is a superset of impact dependency. Keep them distinct in queries and visualizations.

Computed Edge 03

sharesFailureDomain

A sharesFailureDomain B  /  (symmetric)
computed N:M
A and B share a failure domain if they have a common ancestor reachable via locatedIn or runsOn chains; failure of the common ancestor takes both down together.
Traversal definition

Find the lowest common ancestor of A and B in the union of locatedIn and runsOn chains. If one exists, A and B share that ancestor as their failure domain.

Use cases
  • HA design validation: "are my primary and replica in the same rack? Same AZ?"
  • Maintenance window planning: which CIs share a power feed, switch, or hypervisor
  • Risk concentration: detecting unwitting single-points-of-failure across logically independent services
Computed Edge 04

criticalPath

A criticalPath B  /  B underpins A
computed 1:N
The critical path from a business concept A (capability, business application, business service) is the minimum set of infrastructure CIs B whose failure would degrade A — surfaced as the shortest dependsOn / realizes / runsOn chain.
Traversal definition

Starting from A (typically a BusinessCapability or BusinessApplication), perform a shortest-path traversal over realizes → dependsOn → runsOn to reach concrete infrastructure CIs. Each path represents one critical-path segment.

Use cases
  • Executive reporting: "what infrastructure underpins our payment business capability?"
  • Tiered backup & DR planning: which CIs are critical-path for tier-1 business services
  • Cost-to-business attribution: rolling infrastructure cost up to the business outcomes they enable

§ 07 · Validation & enforcement

The triplet system — schema-level correctness.

Every stored edge type has an allowlist of valid (source CI class, target CI class) combinations called triplets. Attempts to write an edge outside its triplet allowlist are rejected at the API boundary, not flagged for later cleanup. This is the central mechanism preventing the relationship-vocabulary drift that legacy CMDBs suffer.

Triplet structure

A triplet is a tuple (sourceClass, edgeType, targetClass) with an optional condition. Examples for runsOn:

Source classEdge typeTarget class
ProcessrunsOnOperatingSystem
OperatingSystemrunsOnVirtualMachine
OperatingSystemrunsOnPhysicalServer
VirtualMachinerunsOnHypervisor

ApplicationrunsOnApplicationServer
ContainerrunsOnKubernetesNode
ContainerrunsOnContainerHost
DatabaseInstancerunsOnOperatingSystem
PodrunsOnKubernetesNode

Triplets are config, not schema

Triplet rules live in JSON Schema files under a versioned config directory in the Fusion SaaS repo. Adding a new valid (source, edge, target) combination is a pull request reviewed by Product and Engineering — not a database migration. This is what allows the catalog to keep up with new infrastructure paradigms without releasing a new database version.

Override mechanism for AI-inferred edges

AI-inferred edges with confidence below 0.85 that would violate a triplet rule are written to a quarantine table, not the main graph. A human reviewer can promote them to the main graph (which either updates the triplet rules or rejects the edge). This is how the system learns new valid patterns without compromising integrity.

Health scoring

CMDB health is scored per CI based on the presence and freshness of its mandatory and common edges (as defined per edge type in §04). Missing mandatory edges score zero on health for that CI. Stale edges (past TTL) reduce confidence. Health is surfaced in the Fusion SaaS dashboard so operators see CMDB decay before it costs them.

§ 08 · Acceptance gates to v1.0

What must be true before this v0.1 becomes v1.0.

This spec ships as v0.1 — proposed, internally aligned, but not yet validated. Three explicit gates must pass before v1.0 freeze. Each gate produces a decision log entry; failures produce edge-set revisions, not workarounds.

Gate 01

Three-scenario modeling pass

Model three real-world systems end-to-end using only the eleven stored edges: (1) full vCenter virtualization stack with external dependencies, (2) Kubernetes multi-pod app with control plane, (3) multi-tier banking application (LB → web → app → DB → cache → identity). Every relationship in each scenario must map to one of the eleven without forcing.

Gate 02

Computed-edge correctness

For each scenario, run all four computed edges and verify the answers match operational reality. False positives in impactedBy (e.g., the vCenter-outage-takes-down-VMs mistake) must not occur. False negatives must be enumerable and explainable.

Gate 03

Discovery integration trial

One real discovery source (agent telemetry or API integration) writes edges through the API. Triplet validation rejects at least one invalid edge during the trial. Evidence and confidence fields populate correctly. Stale-edge surfacing works through one TTL cycle.

After v1.0 lock

All future changes to this spec — adding edge types, splitting an edge type, modifying a triplet rule, changing default impact-edge inclusion — flow through the decision log. v1.0 is the contract engineering builds against; v1.1 is the next contract, never an undocumented drift from v1.0.

Motadata · Fusion SaaS
This specification draws on conceptual precedent from established enterprise CMDB models, refined through a graph-primitive, AI-native lens. Every edge type maps to a battle-tested concept in mainstream CMDB practice; the contribution here is in the orthogonality of the set, the separation of stored from computed truth, and the first-class treatment of evidence and confidence.
