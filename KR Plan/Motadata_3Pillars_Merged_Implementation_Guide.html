Part A - Motadata stack mapped onto ObserveOps

A1) One-sentence purpose

The Motadata PDF is a SaaS-side design: centralize telemetry, keep compact statistics and a typed map, then diagnose with bounded evidence. It is not a second ObserveOps pipeline. Same eleven steps (E1-E11). Pillars are what SaaS stores (and optionally how P3 reasons). Shift-left is where E1-E6 may run.

C Optional P3 diagnose (Layer I / ReAct)
P2 Reads A+B - not a fourth Motadata pillar

A3) Stack picture (write, then diagnose)

Read top to bottom. Left = Motadata names. Right = our pipeline.

  1. Telemetry in (logs, metrics, APM, eBPF, events) -> E1 Collect (admit raw; telemetry only this pass; no CI bind; PDF also lists ITSM here - we do not)
  2. Streaming bus (NATS) - not a pipeline stage; sits between Collect and Stores
  3. A Percentile engine || B Graph builder -> E4+E5 || E3+E5 after identity exists. Windowing is not Node E2.
  4. Vortex + S3 durable lake -> E4 Stores (one dest profile; Gate B: not the only lake)
  5. Case opens - P2 has no Motadata pillar
  6. RCA retrieval layer -> E8 Scope (WorkingSet; do not scan the lake)
  7. C Rust RCA agent -> E9 -> E10 -> E11 (Layer I opt-in)
  8. Explain / ITSM / Remediate -> E11 Package (required VerdictCard; ticket is egress; remediation is outside E1-E11)
  9. Outcome writeback -> E5 Maintain + E3 version

Important gap in the Motadata picture: Identity (E2) is assumed on every sketch and node, but never drawn as a step. We still bind on the Node.

Same clock, SaaS column only. Motadata does not specify OTel Node Collect/Identity, mask/Drain, Detect door A, or optional Gateway door B.

A pillar is not a phase. A and B are always-on P1 stores. P2/P3 only read them. C is Clock B (diagnose/close), optional Layer I.

Take: - mergeable percentile sketches as an E4 modality - typed RCA graph with valid_from/valid_to and confidence as E3 - bounded retrieval as E8 - hypothesis-plus-evidence language for E10 - LLM never owns authorization if Layer I ships

Part C - Pillar 1 deep-dive (Owner: Teammate)

C0) Pillar A in Motadata language (context before implementation)

What: One job, three parts: keep a mergeable percentile, keep a cheap histogram, keep a usual range for this hour of this weekday. Together they answer "is this weird?" without replaying weeks of raw samples.

Why: Weeks of samples cannot be scanned on every alert. Monday 9am traffic is not an outage. Without mergeable summaries and a calendar-aware expected range, Detect lies.

How (Motadata write path): samples (1m/5m/1h/1d) -> T-Digest (mergeable p50/p95/p99) + explicit buckets (fixed bins) + seasonal baseline (hour-of-day x weekday) -> one sketch row per metric + entity + window + season_key -> Vortex/S3

Who reads it (Motadata): - dashboards (O(1) p95 lookup) - E6 door C Detect (threshold / anomaly bound) - E10 Identify (get_metric_baseline())

Example. Checkout p95 = 180 ms. Tuesday 14:00 baseline p95 ~ 200 ms -> normal. Sunday 02:00 baseline p95 ~ 40 ms -> 180 ms is abnormal. Same number; different season_key.

Our pipeline mapping: - writes E4 Stores; writes E5 Maintain (seasonal refresh) - read by E6 door C; read by E10 Identify - not E1/E2 (needs identity first; windowing != Node Normalize) - not E9 leaf rule (percentiles do not name the root CI)

Why both T-Digest and buckets? Percentiles merge cleanly across windows/entities. Buckets make histogram queries and alert rules deterministic and cheap. Seasonal baselines stop business cycles from looking like faults.

C1) How samples are chosen?

What
Choose metric samples by deterministic keys: - tenant - entity_id (or ci_id after E2 identity) - metric_id - window (1m, 5m, 1h, 1d) - timestamp

Only resolved identity rows are sketch-writer eligible.

Why
Without deterministic sample admission, percentile and baseline outputs become non-reproducible across runs and teams.

How
1. Admit only ingest.v1 metric lines with identity.status = resolved. 2. Normalize metric naming (request.latency_ms, cpu.utilization_pct, etc.). 3. Assign each point to one or more configured windows (multi-resolution allowed). 4. Derive season_key from timestamp (for example Mon-09:00, Fri-18:00). 5. Feed sample value into: - T-Digest state for the key - explicit bucket histogram for the key - seasonal baseline accumulator for the key

C2) What does T-Digest do? What is "mergeable p50/p95/p99"?

What
T-Digest is a compressed representation of a value distribution. It supports fast quantile queries (p50, p95, p99) without storing all raw samples.

Why
Raw history scans become too expensive at scale. T-Digest gives near-real-time percentile lookup with bounded storage.

How
1. Each key (tenant, entity_id, metric_id, window, season_key) has a digest state. 2. New values update centroids (compression step). 3. Query asks for quantile q and returns estimate from digest. 4. Mergeable means digest A + digest B -> digest AB: - merge per host -> per service - merge per minute -> per 5-minute rollup - merge shard results -> tenant/global aggregate

Operational meaning: - p50: median behavior (normal center) - p95: high-tail service behavior (SLO-sensitive) - p99: rare tail stress/spike behavior

C3) How explicit bucketing is done?

What
Explicit bucketing is a fixed histogram with predefined boundaries.

Why
Buckets make thresholding, alert rules, and "which range dominates?" questions deterministic and easy to explain.

How
1. Define bucket sets per metric family: - latency: [0-50), [50-100), [100-200), ... - CPU%: [0-20), [20-40), [40-60), ... 2. For each sample, increment exactly one bucket count. 3. Keep total count, min/max, and optional sum for sanity checks. 4. Version bucket policy (bucket_schema_version) to prevent silent drift. 5. Never mix bucket versions in one logical sketch key.

C4) Sketch row format: one row per metric + entity + window + season_key -> Vortex/S3

What
Each row is a compact statistical state for one logical key.

Why
This shape is the contract that allows: - durable archival in S3 - analytical read/index in Vortex - reproducible E6/E10 retrieval without raw re-scan

How (recommended schema v1)

S3 write model (cold / durable)

What: S3 holds cold/large objects and long retention for sketch blobs and history.
Why: Builders are useless if results evaporate; historical UPDATE of raw sample lakes is expensive.
How: - Partition: tenant=.../metric_id=.../window=.../date=YYYY-MM-DD/ - Write mode: append immutable rows; idempotent object naming using key hash + window end - Rollups: optional periodic compaction by day/week

Vortex indexing/read model (hot / analytical)

What: Vortex is the analytical query engine on top of durable data.
Why: Interactive RCA must answer p95 / baseline / trend without scanning raw history.
How: - Primary lookup index: (tenant, entity_id, metric_id, window, season_key, window_start) - Secondary filters: entity_type, date range - First query patterns to optimize: 1. latest p95 for entity+metric 2. compare current window vs seasonal baseline 3. retrieve N prior windows for trend

"O(1)" means cost does not grow with historical sample count. It is still a bounded key lookup + deserialize a sketch.

Gate B remains open: Vortex/S3 may be one dest profile, not the only E4 lake.

C5) How "WHO READS IT" is handled?

What
A role-based read policy for sketch data.

Why
Different consumers need different access levels; unrestricted reads risk data leakage and noisy operations.

How (minimum RBAC plan)

Role May do
role_observability_reader Read sketch rows and baselines; no policy changes
role_detect_engine Read for door-C thresholding (service account only)
role_rca_engine Read for E10 evidence correlation
role_admin_data Manage retention, index configs, schema versions

Controls: 1. tenant-scoped authorization mandatory 2. audit log for each read query (who/what/when) 3. deny-by-default for cross-tenant reads 4. schema-version compatibility checks before query execution

Part D - Pillar 2 deep-dive (Owner: You)

D0) Pillar B in Motadata language (context before implementation)

What: Continuously maintain a typed picture of the estate: what exists, how it connects, and what recently changed. This is an RCA map, not a generic enterprise knowledge graph.

Why: A detector without a map produces an alert. A detector with a map can say which neighbor sits under the symptom, whether a deploy landed, and how sure we are that the link is real.

How (Motadata walk recipe): Incident -> Service (symptom CI) -> deps (CALLS / RUNS_ON) -> Change (CHANGED_BY) -> candidates + abnormal metrics.

Typed edges (subset Motadata lists):
CALLS · DEPENDS_ON · RUNS_ON · CONTAINS · CONNECTS_TO · PRODUCES · CONSUMES · AFFECTS · CHANGED_BY · DEPLOYED_AS · TRIGGERED · CORRELATED_WITH · RESOLVED_BY

Every node/edge carries valid_from / valid_to, confidence, source - so the walk can say why we believe a link.

Example. Pain shows on checkout-api. Walk CALLS -> checkout-db. A CHANGED_BY deploy landed 12 minutes ago on the db. API p95 is high; db p95 is worse. Leaf candidate is the database, not the API.

Our mapping (hybrid, not Motadata copy): - writes E3 Topology GraphSnapshot (SaaS owns it; Gateway only assists) - writes E5 Maintain (versions, change feed, outcome writeback) - read by E8 Scope, E9 Localize, E10 query_graph() - not E6 Detect (storing an Alert != firing Detect) - CI vertices only. Alert/Incident/ticket are not map nodes. Change is a fact, not a CI.

D1) Entities

What
CIs with stable identity (tenant + ci_id) and typed class (Service, Host, optional Pod with validity window).

Why
Localize/package must point to durable operational targets, not transient noise objects. If Alert is a vertex, Curate/Detect leak into E3.

How - allow only resolved identity records for canonical graph vertices - enforce ci_type catalog + versioning - carry aliases as metadata, not alternative primary keys - ephemeral runtime (Pod/Container) allowed only with validity window + parent CI - no Alert, Incident, ITSMTicket, Metric, Trace, LogPattern vertices

D2) Edges

What
Typed CI-CI relationships (for example depends_on, runs_on, communicates_with) with provenance and validity.

Why
E8/E9 walk quality depends on relationship semantics and freshness. Half a real graph is inference; without provenance, confidence is decoration.

How Each edge stores: - source/target IDs - relation type - provenance (authoritative | declared | corroborating) - valid_from, valid_to (or equivalent freshness fields) - confidence / discovered_via as audit metadata

Structure edges (CONTAINS, RUNS_ON) and runtime edges (CALLS, DEPENDS_ON) belong on E3.
Case edges (CORRELATED_WITH, RESOLVED_BY, AFFECTS) do not - they are E7/E11 work.

D3) Changes

What
Time-bound facts linked to CIs (deploy/config/release/change-ticket references).

Why
Change context improves root-cause explainability ("deps -> recent changes -> abnormal metrics") without polluting CI topology.

How - store change as fact records, not CI vertices - link by CI identity and time overlap (CHANGED_BY as hitch, not as a ticket root) - keep change ingestion out of E1 for this block; attach via reserved path/future phase - do not invent a second identity namespace for changes

Part E - Shared lake, retrieval, build order

E1) Vortex + S3 (rooms, not products to argue about)

What: Two rooms in one Motadata warehouse: historical observability (sketches/history) and knowledge graph (who is connected). Same entity_id / ci_id namespace.

Why: Builders are useless if results evaporate. RCA must not mutate history in place.

How: Percentile engine and graph builder write in parallel after identity exists. S3 holds cold/large objects; Vortex is the analytical engine. Agent never opens this as a dump - it goes through retrieval.

Our resolution: Keep rooms logically separate (E3 map || E4 evidence). Vortex/S3 may be one dest profile (Gate B open). Node/Gateway only buffer - they are not the lake.

E2) RCA retrieval layer (P2 reader, not a pillar)

What: A bounded index in front of the lake: give me these evidence kinds for this seed under these limits. In our language: WorkingSet.

Why: Unscoped RCA walks the estate and hallucinates. Cost, latency, and wrong neighbors explode.

How: Start from curated seed (not raw alert storm). Expand k hops. Pull baselines, events, changes inside time window. Stop when budget spent. Then Localize.

Four kinds in: baseline (A), graph (B), events (Detect storm), changes.
Four knobs: time window, entity scope, hop count, evidence budget.

Example. Seed = checkout-api at 14:02. Budget: 30 minutes, 2 hops, 40 evidence items. You get the API, its db, last deploy, p95 vs Tuesday baseline - not the whole cluster.

E7 Curate still runs first - one CaseSeed. Retrieval does not merge the storm (D3).

E3) Pillar C note (out of this block, but needed for context)

Motadata default closer is a Rust ReAct agent with typed tools and a policy engine.
We keep it as optional Layer I (D5 Review). Operator E9-E11 on A+B must work with agent off. Do not fold Curate into the agent. Remediation is outside E1-E11.

E4) Recommended implementation order

Do not ship A -> B -> C as three products. A and B are parallel P1 writers after E2 keys exist. C is last and opt-in.
